## 0. 为什么"加三个工具"值得写一份文档

`docs/UNIMPLEMENTED-2026-09-27.md` 里对写操作有一句判断：

> **关于写操作**：文件管理器目前是纯只读的。加删除/重命名意味着引入新的权限等级（L2 敏感写），需要走 `Gate` 闸门与确认卡片 —— 这是**权限模型的问题，不是 UI 的问题**，应该和 `docs/ai-permissions.md` 一起设计，不要顺手加。

这份文档就是那次"一起设计"的落地记录。三个工具本身很简单，**难的是三条约束**：

1. 所有新入口必须走 `Gate::judge`（**不要**另加 `Request` 变体 —— 那是 P1-1 的形态）；
2. 删除先进回收站，且回收站有容量上限与过期清理；
3. 审计先补齐 —— 否则 L2 写操作没有追溯手段（4.3b 已完成，这条是它的存在理由）。

## 1. 写白名单必须比读白名单窄（本次最重要的设计决策）

| | 允许根 |
|---|---|
| **读**（`READ_ALLOWED_ROOTS`） | `/home`、`/etc/aether`、`/var/log/aether`、`/run/aether`、`/tmp` |
| **写**（`WRITE_ALLOWED_ROOTS`） | `/home`、`/tmp` |

**为什么不复用读白名单**：

- 写 `/etc/aether` = 让 AI 修改**自己的权限规则**（提权）；
- 写 `/var/log/aether` = 篡改**审计记录**（灭证）。

这两条都不是"文件编辑"，是攻击面本身。所以写白名单把它们排除在外。

**这条不变量有测试守着**（`write_roots_are_subset_of_read_roots`）：写白名单必须是读白名单的子集。比逐条列举路径更耐改 —— 将来有人往写白名单加目录，若它不在读白名单里，测试会红。

另有 Linux 专属断言（`linux_write_excludes_aether_own_config_and_logs`）：配置与日志**可读但不可写**。

### 路径校验的两个差异

`resolve_writable` 与 `resolve_readable` 有两点不同：

1. 允许根更窄（上表）；
2. **目标可以尚不存在**（新建文件、重命名到新名字）—— 此时 `canonicalize` 会直接失败，所以改为"规范化**父目录** + 拼上文件名"。

仍然先 canonicalize，因此 `..` 穿越与符号链接绕行同样被堵死。凭证类子路径（`.ssh` 等）在写侧也拒绝 —— 它们本来就在允许根**之内**。

## 2. 回收站

**布局**（每个条目一个目录，元数据与内容分开）：

```text
/var/trash/
  1759000000-1/
    origin     ← 原绝对路径（纯文本）
    payload    ← 原文件或目录（原样搬过来）
```

**为什么用 `rename` 而不是"复制 + 删除"**：同盘 rename 是原子的，中途断电也不会出现"原文件没了、回收站里也没有"的窗口。

**先写 `origin` 再搬 `payload`**：中途失败最多留下一个**空条目**，而不是"数据没了但不知道原来在哪"。

**容量策略**（`Policy::default()`）：条目数 200 + 总字节 256MB + 存活 7 天，三者任一超限都从**最旧的**开始清。

> 回收站自己没上限的话，它只是把"磁盘满"从用户目录挪到了回收站 —— 那是把问题推迟，不是解决。

条目名以 unix 时间戳开头，因此**字符串倒序即时间倒序**，清理时不必额外排序。同一秒内多次删除靠序号区分（有测试覆盖）。

**恢复不覆盖已存在的文件** —— 宁可让用户先处理，也不要静默盖掉。

**条目名来自外部输入**（IPC），所以 `restore` 校验：空、含 `/`、含 `\`、含 `..` 一律拒绝。

## 3. 三个工具

| 工具 | 等级 | 参数 | 说明 |
|---|---|---|---|
| `file_write` | **L2** | `path`、`content`（≤256KB） | 覆盖或新建。超长**整体拒绝**，不产生半个文件 |
| `file_delete` | **L2** | `path` | **移入回收站**，不做永久删除 |
| `file_rename` | **L2** | `from`、`to` | 目标已存在则拒绝（不覆盖） |

三者的 `consequence` 文案都会显示在确认卡片上（例如删除的："移入回收站，可从回收站恢复；但超过 7 天、或回收站条目/容量超限时会被自动清理"）。

`file_write` 的后果说明特别注明"原有内容不会进回收站，直接不可恢复" —— **覆盖与删除的不可逆性不同**，用户需要知道这个差别。

## 4. UI 入口

**真机（`run_fbdev`）与预览（`preview_main`）两条事件循环都接了 `Delete` 键**：

```rust
if nav == input::NavKey::Delete {
    if let Some(msg) = request_delete(&desktop, &tx) { toast = Some((msg, ...)); }
}
```

`request_delete` **只发起，不执行** —— 它把 `ToolCall{file_delete}` 发给 aetherd，服务端判 L2 → 回 `NeedsConfirmation` + 令牌 → 主循环弹确认卡片 → 用户点「允许一次」才真的删。

**为什么不在 compositor 本地直接删**：那会绕开闸门与审计。删除必须走 IPC。

**重命名 / 新建**：目前通过 AI 指令条（自然语言）触发。UI 直接输入新名字需要文本输入框，属 2.4（统一文本交互）的范畴。

== 三、新建/覆盖：走确认 ==

### 5.2 审计记录（验收要求"审计有记录"）

```
1790567267  L2 敏感写  file_delete  {"path":"…\\victim.txt"}   needs_confirmation
1790567267  L2 敏感写  file_delete  {"path":"…\\victim.txt"}   allowed
1790567267  L2 敏感写  file_rename  {"from":"…\\old.txt",…}    needs_confirmation
1790567267  L2 敏感写  file_rename  {"from":"…\\old.txt",…}    allowed
1790567267  L2 敏感写  file_write   {"content":"AI 写的内容",…} needs_confirmation
1790567267  L2 敏感写  file_write   {"content":"AI 写的内容",…} allowed
1790567267  L2 敏感写  file_write   {"content":"x","path":"C:/Windows/win.ini"} needs_confirmation
1790567267  L2 敏感写  file_write   {"content":"x","path":"C:/Windows/win.ini"} allowed
1790567267  L2 敏感写  file_write   {"content":"x","path":"C:/Windows/win.ini"} failed
```

两点值得注意：

1. **每次写操作都是 `needs_confirmation` + `allowed` 两条** —— 证明"用户确认过"是服务端的事实，不是本地 UI 状态；
2. **路径拒绝的是 `allowed` + `failed`** —— 闸门放行（用户确实批准了），但路径白名单拒绝。**这两件事在审计里可区分**，这正是 4.3b 补上 `failed` 裁决值的意义。
