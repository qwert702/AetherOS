## 二、根因分析

修前的 workflow 把所有门禁塞进一个 job：

```text
gates.py --online
  ├─ cargo build / cargo test
  ├─ e2e（无界面）
  ├─ 像素回归（依赖字体/渲染环境）
  ├─ 布局几何（依赖字体/渲染环境）
  ├─ 性能门禁（依赖稳定帧时间）
  └─ ...
```

这条链路在开发机（有 `target/` 缓存、字体、稳定环境）能跑，但在 GitHub 托管 runner 上不成立：

1. **字体与显示环境不稳定**：像素/布局门禁需要仓库里没有入库的字体产物（`platform/overlay/usr/` 被 `.gitignore` 忽略），干净 checkout 下可能退化或失败；
2. **性能门禁本身受 runner 负载影响**，不适合作为每次 push 的硬门禁；
3. **单 job 串行**：前面的全量门禁一红，后面的 Linux 专属 `cargo test` 永远不执行——这正是 CI 本来要补的洞；
4. **Linux 构建依赖未显式安装**：`minifb` 需要 X11/xkbcommon 开发库，Ubuntu runner 不保证预装。

## 三、修复方案

### 1. `scripts/gates.py` 新增 `--ci`

`--ci` 只跑：

- `cargo build --workspace --all-targets --locked`
- `cargo test --workspace --locked`
- 全部快速门禁（文档、站点、链接、依赖声明、纯函数自检）

不跑依赖字体/显示/计时的像素、布局、性能门禁；不静默跳过——在文档中写明由构建机执行。

同时新增 `--log-dir`，把每一步完整输出落盘，便于 CI 失败时上传 artifact/排查。

### 2. `.github/workflows/ci.yml` 拆成两个 job

| Job | 平台 | 内容 |
|---|---|---|
| `fast` | ubuntu + windows | `python scripts/gates.py --fast` |
| `test` | ubuntu + windows | `cargo build --workspace --all-targets --locked` + `cargo test --workspace --locked` |

Ubuntu 的 `test` job 会安装 `libx11-dev`、`libxkbcommon-dev`、`libxkbcommon-x11-dev`、`libxcb1-dev`、`libwayland-dev`，并真实执行 `cfg(unix)` / `cfg(target_os = "linux")` 分支。

### 3. 全量门禁的归属

像素、布局、性能门禁仍在构建机/自托管 runner 上跑，命令：

```bash
python scripts/gates.py          # 全量 41 项
```

它们不再阻塞每次 push，但仍保留在发布前的手工/构建机验收清单里。
