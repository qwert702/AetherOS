# 自动更新链路（P1）—— 证据与边界 · 2026-10-17

> **一句话**：文件级自动更新（应用/配置/状态）的三段链路都已实现并**逐段验证**；
> **系统组件（内核/合成器/init/aetherd）刻意不走这条路**，它们走"新 ISO + 无人安装 + `--keep-var`"（T3）。
>
> **还没验的**：真机端到端（guest 拉到 → 重启生效）与生产发布 —— 两者都卡在"需要虚拟机/需要人点头"，
> 不是代码没写。诚实标注在这里，不冒充完成。

## 一、它长什么样

```
宿主                                                         guest
──────────────                                               ─────────────
① mkupdate.py --version 0.1.2 --from <暂存树> --out updates/
      产出 updates/0.1.2/{update.json, var/apps/...}

② publish-updates.py updates/0.1.2 --apply
      摊平上传到 <base>/update.json 与 <base>/<path去掉开头的 />      ← 同一份 <base>
                                                                   ③ aetherd::updater 定时：
                                                                      GET <base>/update.json
                                                                      → version_is_newer（拒降级）
                                                                      → 逐文件下载（.partial 临时名）
                                                                      → verify_bundle（哈希+大小不符整包拒绝）
                                                                      → 投 incoming/<version>/
                                                                      → stage() 暂存
                                                                   ④ 下次启动 PID 1 按 apply.list 应用
```

### 白名单（刻意很小）

```
TARGET_PREFIXES = ["/var/apps/", "/etc/aether/", "/var/lib/aether/"]
```

**没有 `/usr/bin/`** —— 原注释写着"没有白名单的话它就成了以 root 写任意文件的工具"。
系统组件走整机路径，见本文件开头。**`mkupdate.py` / `publish-updates.py` / Rust 侧三处判据必须同时改。**

## 三、本轮踩到的环境坑（都花了时间，记下来省下次）

| # | 事实 | 对策 |
|---|---|---|
| 1 | **VMware 便携版没有 CLI 按键注入**，`vmrun` 也拉不起/看不到 GUI 启动的 VM | guest 内一切必须**引导期自动**或**自触发**；换盘只能先人工关机 |
| 2 | 那台 VMware VM 的**串口落盘不稳定**（`serial.txt` 常为 0 字节，最慢 35 分钟才出现）| 判据不能只靠串口：叠加"磁盘文件长大 / 结果标记 / 人眼看一眼" |
| 3 | **VirtualBox 有** `screenshotpng` + `keyboardputscancode`（VMware 都没有）| 构建机卡住时可以注入按键救回来（实测：GRUB 菜单**一个回车**就好）|
| 4 | 但**当前模型读不了图** ✗ | 截屏只作存档；**人在旁边看一眼最快**（这次就是靠这个定位的）|
| 5 | 构建机的**串口是死的**（恒 0 字节）| 不要指望它；诊断靠 SSH / 截屏 / 问人 |
| 6 | 对构建机**硬断电**后，下次会停在 **GRUB 菜单** | 只用 `acpipowerbutton`；真断电了就发**一个回车** |
| 7 | ISO 的根文件系统是**压缩**的 ⇒ 明文字符串搜不到 | "搜不到" ≠ "不存在"：要在**打包前的二进制/overlay**上验 |
| 8 | 同日三次用**宽正则**同步文档数字，三次改坏别处 | 固化成 `scripts/follow-gate-numbers.py`：照判据打印的"声明 X / 实测 Y"精确回填 |

## 五、2026-10-24 增补：清单签名（Ed25519）

**背景**：此前更新链路的信任锚只有 HTTPS + 同源 SHA-256 清单。服务器被攻破时，
攻击者可以同时替换清单与包，`aether-init` 会以 root 应用 —— 哈希校验挡不住"同源替换"。

**修法**：

| 环节 | 变化 |
|---|---|
| 公钥 | `aetherd/keys/update_pubkey.bin`（32 字节原始 Ed25519 公钥，可入库） |
| guest 下载 | 同时拉 `<base>/update.json` 与 `<base>/update.json.sig`；**先验签、后解析** |
| 验签实现 | `aetherd/src/update.rs::verify_manifest_signature`（`ring::signature::ED25519`） |
| 宿主打包 | `scripts/mkupdate.py --signing-key ~/.aether/update-signing-key.pem` 产出 `update.json.sig`（64 字节） |
| 发布 | `scripts/publish-updates.py` 强制要求 `.sig`，缺签名拒绝发布 |
| 开发开关 | `AETHER_ALLOW_UNSIGNED_UPDATE=1`，仅本地开发；启动日志显式告警 |

**密钥纪律**：

- 私钥只放仓库外（默认 `~/.aether/update-signing-key.pem`，0600），**绝不入库**；
- 公钥 SHA-256 指纹：`c4e3d941026ac876d29665a307fbfabc01d40cee10e53c5cfaeaca2c96b65d01`；
- 私钥丢失 = 无法再签新更新；请离线备份。轮换公钥等于旧客户端不再接受新清单，要走发布流程。

**验证**：

- Rust 单测 7 项：正确签名通过、篡改清单拒绝、截断签名拒绝、错公钥拒绝、错长度拒绝、生产公钥长度；
- `mkupdate.py --selftest`：签/验闭环 + 篡改负向；
- `publish-updates.py --selftest`：缺签名拒绝；
- `update-contract-check.py`：真实 HTTP 布局中包含 `update.json.sig`，按 guest URL 可取到 64 字节。

**仍未做**：真机端到端（签名包 → guest 拉取 → 重启生效）；需要 VM 关机 + 人工验收。
