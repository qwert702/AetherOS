# AetherOS AI 权限模型 v0

原则：AI 无所不知（可读），但不会不问就动手（受控可写）。

## 权限等级

| 等级 | 名称 | 示例 | 策略 |
|---|---|---|---|
| L0 | 只读 | 查状态、读文件、列目录 | 直接执行，记审计日志；**路径受白名单约束**（见机制 3） |
| L1 | 可逆写 | 改壁纸、开/关服务、移动窗口 | 直接执行，记日志，可一键撤销 |
| L2 | 敏感写 | 装卸软件、改系统设置、删除用户文件 | 弹确认卡片，用户点头才执行 |
| L3 | 危险 | 格式化、改内核参数、批量删除、网络开放端口 | 双重确认 + 输入确认短语 |

## 机制

1. **能力标签**：每个工具调用声明所需等级；aetherd 内置等级表，工具无法自我提权。
   `install_disk`（整盘擦除）为 L3：除等级闸门外，还要求 `confirm` 参数回显目标盘设备名。

   **入口规则**（2026-09-28 补）：`aetherd/src/server.rs::handle_request` 的权限检查是
   **逐分支手写**的，所以"新增一个 `Request` 变体"就等于"新增一处可能漏检的入口"。
   因此：
   - 任何能**读用户数据**或**改系统状态**的请求，必须走 `Gate` 或要求已注册的 UI 通道；
   - 该约束由 `server.rs::ipc_gating_tests::request_variants_are_gated` 固化成门禁 ——
     新增变体若忘了加门槛，测试会红。这条测试本身就是第四轮审查（P1-1）的产物。

2. **审计日志**：所有 AI 操作落盘 `/var/log/aether/aether-audit.log`（追加写，含等级、工具、参数、裁决）。
   审计写入失败不阻断执行，但错误会显式返回调用方并落 stderr，不允许静默零留痕。

   裁决列取值：

   | 值 | 含义 |
   |---|---|
   | `allowed` | 闸门放行（L0/L1，或 L2+ 已带有效令牌） |
   | `needs_confirmation` | L2+ 未获确认，已下发确认请求 |
   | `denied_by_user` | 用户在确认卡片上点了"拒绝"，令牌被撤销 |
   | `denied` | 该操作此前被用户拒绝过，冷却期内直接拒绝（不再重复询问） |
   | `failed` | 闸门放行但工具执行失败（含路径白名单拒绝），与"真的执行成功"区分开 |
   | `rejected_no_ui` | **未注册为 UI 通道**的连接发起了受限请求（剪贴板 / L2+ 令牌兑现）。这不是"用户拒绝"，而是**入侵尝试信号** —— 单独取值才能在审计里回答"有没有人在敲门" |

   实现里这些取值是 `perm::verdict` 模块的常量，调用方不再写字面量。

3. **只读也有边界**：`read_file`（L0）只能读**用户数据区**与 aether 自身的配置/日志。
   - 允许根（Linux）：`/home`、`/etc/aether`、`/var/log/aether`、`/run/aether`、`/tmp`
   - 拒绝：`/etc` 其余部分、`/proc`、`/sys`、`/dev`、`/boot`、`/root` 及任何白名单外的路径
   - 路径先 `canonicalize` 再校验，因此 `..` 穿越与符号链接都绕不过去
   - 白名单根之内的凭证类子路径（`.ssh`、`.gnupg`、`.aws`、`.kube`、`.netrc`、`id_rsa` 等）仍然拒绝

   实现理由：aetherd 以 PID 1（root）运行，没有路径约束的"只读"等于"可读 /etc/shadow、/proc/self/environ"。

4. **确认令牌绑定确认方**：L2+ 操作会签发一次性令牌（128 位、5 分钟、用后即废、绑定 tool+参数），
   但令牌本身**不等于放行权**——只有**已注册的 UI 通道**能兑现它。

   - 客户端连接后先发 `Request::RegisterUi { key }`；密钥来自 `AETHER_UI_KEY` 环境变量，
     或 aetherd 首次启动时生成并写入 `/run/aether/ui.key`（Unix 下 0600）
   - 未注册连接：既不会收到确认令牌（L2+ 请求被直接 403），也不能兑现令牌（403）
   - **资源敏感的工具按资源判，不按入口判**：剪贴板读写（`clipboard_read` /
     `clipboard_write`）无论走 `Request::ClipboardGet/Set` 还是 `Request::ToolCall`
     都要求已注册通道；判定表只有 `tools::TRUSTED_CHANNEL_TOOLS` 一处
     （2026-10-02 审计 H-2：此前只堵了协议端点，工具路径仍可读写）
   - 因此"任何能连上 7311 的进程都能自助放行"不再成立

   诚实边界：这挡不住**能读到密钥文件**的本机进程。IPC 尚无用户级认证（M4 规划），
   所以它是"提高门槛 + 让确认方成为服务端可断言的事实"，不是完整的多方授权。

   > 2026-10-02 审计补充（M-17）：**注册走 Unix socket（`/run/aetherd.sock`，0600）**，
   > 不再默认走 TCP —— 因为 TCP 上客户端无法验证对端，谁抢到 7311 谁就能收到密钥。
   > 同时密钥文件已从 `/var/log/aether/` 迁到 `/run/aether/`，并从 `read_file` 的
   > 可读范围里排除（H-1）。TCP 仍监听，但只用于开发机调试（需显式 `AETHER_IPC_TCP=1`）。

   > 2026-10-02 审计补充（H-1）：密钥文件曾放在 `/var/log/aether/`，而该目录
   > **在 `read_file` 的读取白名单内** —— 于是"任意本机进程 → ToolCall(read_file)
   > → 取走密钥 → 注册 UI → 自我确认 L3"是一条完整链路（已实测复现）。
   > 现在密钥迁到 `/run/aether/`，且 `read_file` 的凭证类拒绝清单包含 `ui.key`。

5. **拒绝是服务端的事实**：用户在确认卡片上点"拒绝"时，合成器会发送
   `Request::ConfirmCancel { token }`。服务端据此撤销令牌、落 `denied_by_user` 审计，
   并把该 (tool, 参数) 记入 300 秒拒绝冷却——冷却期内同一操作**直接 `denied`**，
   不再反复弹卡片。此前"拒绝"只存在于合成器的本地 UI 状态里，服务端既不撤销令牌也无留痕。

6. **读到的文件内容不上云**：混合推理路由**不再用"消息条数"判断复杂度**
   （每轮工具调用会给消息表 +2 条，旧规则导致"任何多轮工具任务在第 3 轮必然上云"）。
   现在 `read_file` 被标记为敏感输出：其结果一旦进入上下文，本轮推理强制走本地通道。

7. **撤销栈**（规划中，未实现）：L1 操作自动生成逆操作；AI 面板提供"撤销上一步"

8. **熔断**（规划中，未实现）：单位时间 L2+ 调用超阈值自动挂起会话，防止提示词注入导致的连环操作

9. **注入防线**（规划中）：外部内容（网页、文件）进入 AI 上下文时打标记，其中的指令不视为用户指令

10. **剪贴板是受限端点**（2026-09-28 第四轮审查补）：跨进程剪贴板
    （`Request::ClipboardGet` / `ClipboardSet`）与 L2+ 令牌**同一门槛** ——
    只有已注册的 UI 通道能读写，未注册连接一律 403 并落 `rejected_no_ui` 审计。

    为什么需要：剪贴板常被用来复制密码，而它的 IPC 入口最初**绕过了整套闸门** ——
    因为它走的是 `Request` 变体而不是 `ToolCall`，而 `handle_request` 的权限检查是
    逐分支手写的。当时任何能连上 7311 的本机进程都能无门槛读写（P1-1）。

    配套约束：

    | 约束 | 理由 |
    |---|---|
    | `clipboard_write` 工具是 **L1**（可逆写），不是 L0 | 写操作不能标"只读"；且当时读（L1）比写（L0）级别高，方向是反的 |
    | 内容有 **300 秒存活上限**（`clipboard::TTL`） | aetherd 以 root 运行，内容永久驻留内存等于给"AI 能读到的敏感数据"开永久窗口 |
    | 合成器只把**显式拖选**的终端内容同步给 aetherd | 无选区时复制的是**整屏**，可能含 `cat /etc/shadow` 类输出；随手按一下复制键不该等于"授权 AI 读取这一屏" |
    | 合成器推送前先注册 UI 通道 | 顺带消掉端口劫持：冒充 aetherd 的进程拿不到 `ui.key`，注册不过去 |

11. **写操作的白名单比读窄**（2026-09-28 · 4.1 补）：`file_write` / `file_delete` /
    `file_rename` 三个工具都是 **L2**（弹确认卡片），且写路径白名单**不含**
    aether 自身的配置与日志。

    | | 允许根 |
    |---|---|
    | 读 | `/home`、`/etc/aether`、`/var/log/aether`、`/run/aether`、`/tmp` |
    | 写 | `/home`、`/tmp` |

    为什么：写 `/etc/aether` = 让 AI 改**自己的权限规则**（提权）；写
    `/var/log/aether` = 篡改**审计记录**（灭证）。这两条不是"文件编辑"，是攻击面本身。
    该不变量由测试守着（写白名单必须是读白名单的子集）。

    **删除先进回收站**（`/var/trash`），带条目数 / 总字节 / 存活天数三重上限 ——
    回收站自己没上限的话，它只是把"磁盘满"从用户目录挪到了回收站。
    恢复**不覆盖**已存在的文件。

    审计表现：一次写操作留 `needs_confirmation` + `allowed` 两条（证明"用户确认过"
    是服务端的事实）；若路径被白名单拒绝，则是 `allowed` + `failed` —— **闸门放行
    与执行失败在审计里可区分**。
