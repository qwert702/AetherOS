### 1.1 P1-8 的实测比上轮更严重：是「跨连接」兑现，不是「同连接」

上轮证明的是"同一条连接内可自助兑现"。本轮实测（`scripts/_repro-adversarial.py`）：

```
  [连接#1] 无令牌请求 -> type=needs_confirmation level=3
           签发令牌 = 3bb60f8bc98665afe5cd700be42e47f7
  [连接#2] 用连接#1 的令牌重发 -> type=tool_result
           output = '[工具错误] 安装器运行失败: 系统找不到指定的路径。 (os error 3)'
  >>> 判定：令牌跨连接可兑现 = 闸门可被自助放行（P1-8 仍存在）
```

**令牌连"同一条连接"都不需要** —— 任意能连上 7311 的进程，只要拿到（或猜到/截获）令牌，就能兑现。上轮的"最低成本临时措施"（校验兑现连接 ≠ 发起连接）**按当前实测已不足以修复**，必须绑确认方身份。

### 1.2 一个更尖锐的事实：这个缺陷被写进了官方验收标准

`scripts/e2e-permission-confirm.py` 的第 2 项断言是：

```python
r = rpc([toolcall(DISK, token)])[0]      # rpc() 内部每次都 create_connection —— 全新连接
check("2 令牌放行到工具体", r["type"] == "tool_result", ...)
```

**官方 e2e 脚本的第 2 项断言，本身就是"新连接用他人令牌被放行"的证明**，且它以 PASS 为期望值。也就是说：P1-8 不是"没测出来"，而是**被当成了正确行为固化进测试**。修复 P1-8 需要同时修改这条断言（否则测试会变红）。

### 1.3 对上轮报告一处措辞的修正

上轮 P1-9 写"`docs/ai-permissions.md` 定义了 `Denied` 这一档语义"。核实：**该文档并未定义 `Denied`** —— 它只有 L0–L3 四档权限表（`ai-permissions.md:7-12`），`Denied` 只存在于 `perm.rs:54` 的 `Verdict` 枚举里。缺陷本身（拒绝通路不通）成立，但"文档定义了该语义"这一论据不准确，此处修正。

### P2-20 主操作按钮「允许一次」的文字对比度不达标（深色 2.07:1 / 明亮 4.11:1）

确认弹窗里唯一的"放行"按钮，文字与底色对比度实测低于 WCAG AA 正文标准（4.5:1）。

- 位置：`aether-compositor/src/draw.rs:2086-2088`
  ```rust
  let (lrgb, la) = if ready { (color::text(), 0.98) } else { (color::text_faint(), state::DISABLED) };
  tr.draw_bold(..., "允许一次", font::BODY, lrgb, la);
  ```
  按钮底为 `color::accent()`（`draw.rs:2076`），文字取 `color::text()` —— **两模式都是"底色取强调色、文字取主文字色"**，而这两个值在两种模式下都是低对比组合。

实测（`extrema`/`contrast` 命令，区域取按钮内部纯色区 `x[760,794] y[496,508]`，避开文字与圆角抗锯齿）：

| 模式 | 底色实测 | 文字实测 | WCAG 对比度 | AA 正文要求 |
|---|---|---|---|---|
| 深色 | `rgb(63,183,198)` | `rgb(236,239,245)` | **2.07:1** | 4.5:1 ❌ |
| 明亮 | `rgb(23,138,155)` | `rgb(25,30,36)` | **4.11:1** | 4.5:1 ⚠️ |

- **深色模式 2.07:1** 不仅低于正文 4.5:1，甚至低于大字号 3.0:1 的门槛 —— 浅色文字压在亮青色实心块上，是最难读的组合之一。这是**历史遗留**（上一轮未发现，本轮首次量化）。
- **明亮模式 4.11:1** 是本轮新增的，已明显好于深色（说明双模重构顺带改善了这个点），但仍未达标。

**修复方向**：按钮底改为更深的强调色变体（如 `mix(accent(), [0,0,0], 0.25)`），或文字改用纯白（明亮模式需配更深的底）。建议一并核对所有"强调色实心底 + 文字"的组合（Dock 图标符号、AI 徽标 "A"、播放/暂停控件同属此类）。

> 严重级别定 P2 的理由：不影响功能与安全，但这是**权限确认链路上最关键的一个按钮** —— 用户在这里做不可逆决定，文字读不清会直接影响"知情同意"的有效性。可访问性缺陷，且已量化。

### P3-28 `fill_rect` 的 `(rect.x + rect.w) as usize` 存在整数回卷（历史遗留，未构造出可达序列）

- 位置：`draw.rs:396` `let x1 = ((rect.x + rect.w) as usize).min(w);`
- `rect.x + rect.w` 是 `i32` 运算，**负值 `as usize` 会回卷成巨值**，再 `.min(w)` 得到 `w` → 若 `rect.x` 为负且 `x+w < 0`，会**误填整行**。
- 该行的防御只覆盖了 `rect.w <= 0`（`draw.rs:391`），未覆盖 `rect.x + rect.w < 0`。

引入自首个提交 `0e9bf54`，非本轮引入。本轮逐个核对了全部调用点：`draw_icon_grid` 的 `ox` 受 `if avail_w < CELL_W { return 0 }` 保护不会为负；其余调用点均为编译期正数或已 clamp。**未构造出可达序列**，故仅列为 P3。

**修复方向**：`let x1 = ((rect.x + rect.w).max(0) as usize).min(w);`（一行，顺带把 `y1` 一并处理）。

## 3. 本轮正面结论

### 3.1 双模主题的架构是干净的（一次真实且克制的重构）

- **常量 → 函数**改造彻底：全仓 `color::[A-Z_]{3,}` 形式的残留**只有 `color::HIGHLIGHT`**（7 处），而它按设计就是"两模式皆白"的常量（`draw.rs:105`）。172 个调用点的正则改写**没有留下一个漏网的常量**。
- **语义 token 设计成立**：`hairline()`（深色白/明亮黑）、`glass()`+`glass_alpha()`、`scrim()`+`scrim_alpha()`、`aurora_*()`、`elev_*()` 六个 token 让绝大多数调用点无需模式判断 —— 这是"低成本双模"能成立的关键，作者判断正确。
- `set_mode()` 在 `main()` 最开头调用（`main.rs:872-882`），早于一切线程创建与绘制，`AtomicU8` + `Relaxed` 在此场景下无可见性问题。

### 3.2 明亮模式的渲染是**可复现的**（逐像素 0 差异）

用当前二进制重新生成明亮截图，与归档图**逐像素完全一致（884520 像素中 0 个不同）**：

```
A=target/uishot/_repro-light2.bmp        （当前二进制 --shot 2 --theme light）
B=docs/host-ui-light-desktop.png         （归档）
  比对像素 884520  不同 0 (0.000%)
```

这说明：**软件光栅化管线是确定性的**（除时钟与 AI 光标相位），明亮模式的归档图可信、可作回归基线。与 P2-19 的深色归档形成鲜明对比 —— 同一个项目里，明亮归档是对的，深色归档是坏的。

### 3.3 明亮模式的视觉质量确实达到了目标

目视 `docs/host-ui-light-{desktop,confirm}.png`：近白底 + 四角粉彩壁纸、三级明度阶梯（底座 226 < 窗口 242 < 纸面 255）、白玻璃悬浮层、轻而明确的阴影、Dock 图标"上亮下暗"受光 —— 与"苹果风、明亮通透、留白充足"的目标一致。handover §12.2 记录的四个陷阱（明度阶梯重排、悬浮层必须白玻璃、浅色不能用极光带、阴影强度 0.17）**都在代码里真实落地了**（逐条核对了对应调用点）。

### 3.4 权限链路的功能正确性未回归

13 项断言全 PASS：L3 拦下并下发结构化确认（等级/回显目标/后果/令牌/参数明文）、令牌一次性、令牌绑定参数、L1 不受影响。**功能是对的**；问题在于它防的是"模型"而不是"别的进程"（P1-8）。

## 4. 未验证清单（明确不计入上述结论）

1. **Linux 实机行为**：全部复现在 Windows 上完成。`aetherd` 以 root 运行、`read_file` 可读 `/etc/shadow` / `/proc/self/environ` 等，均为**源码推断**（可信度高，未实机验证）。本轮 `read_file("C:/Windows/win.ini")` 成功只证明了"无路径约束"这一点，未证明敏感文件的可达范围。
2. **P0-4 的上云链端到端**：本轮未重跑双假 LLM 端点。依据是"`aetherd` 源码与二进制均未变（cargo 未重编译）→ 上轮的端到端实证继续成立"。这是**基于不变性的推论，不是本轮实测**。
3. **真实提示词注入**：未构造能让模型主动读取敏感文件的输入。上轮用假端点直接下发 `read_file` 作为替身。
4. **`scripts/shot-diff.py`**：本轮**未能运行** —— 它需要 `before-r1-l*.bmp` / `before-r2-l*.bmp` 作为输入，这些文件不在仓库中（`target/shots/` 里只有 `after-*.bmp`）。该脚本自身注释也写明"Step 3 之后不要再用它作为验收门槛"。本轮改用自建解码器直接做归档比对（§2 P2-19），覆盖了同样的目的。
5. **交互态**：拖拽、悬停、窗口动画的目视未做（需交互桌面）。`--mouse X Y` 走查参数存在，本轮未逐态出图。
6. **`shadow()` 多窗口性能**：`elevation` 的 5 层叠加在 10fps 下是否掉帧，仍未实测（handover §P4-2 自述，本轮未补）。
7. **P3-28 的可达性**：未构造出 `fill_rect` 整数回卷的触发序列。
8. **深色其余归档图**：`host-ui-confirm/menu/threecol.png` 同为 20:07 产物，**按同一时间线推断同样停留在 §9**，但本轮只对 `desktop` 做了逐像素比对，其余三张未逐一验证。

## 6. 一句话总结

**这一轮是纯 UI 工作，代码质量依然在线**：双模主题的常量→函数改造彻底（172 个调用点零遗漏）、明亮模式渲染确定性可复现（逐像素 0 差异）、视觉质量确实达到了"苹果风"的目标、65 项测试全绿、权限链路 13 断言全过。

**但有三件事必须点破**：

1. **安全边界这一轮原地踏步** —— 本轮一行未动 `aetherd`。上轮的 P0-4（`read_file` 任意读 + 多轮必上云）、P1-8、P1-9 **全部原样存在**，且 P1-8 的实测结论比上轮**更严重**：不是"同一连接可自助兑现"，而是**任意新连接都能兑现他人触发的令牌** —— 而这个行为正被官方 e2e 脚本当作正确结果固化。

2. **本轮唯一一处"声称与实测不符"** —— `2cccb6a` 提交信息称"深色像素级零回归：与 host-ui-desktop.png 逐像素比对，壁纸区平均差 0.0"。实测两张图差 1.727%、最大差 15。深色代码本身没回归（对 `D-regress.png` 是 0 差异），**坏的是归档图停留在 §9 从未更新**，导致这个结论和后续所有基于该图的回归都不可信。

3. **一个被量化出来的可用性缺陷** —— 权限确认弹窗里唯一那个"放行"按钮，文字对比度深色 **2.07:1**、明亮 **4.11:1**，均低于 WCAG AA 的 4.5:1。用户在做不可逆决定的地方，字是看不清的。

L3 擦盘有回显门挡着，但 `read_file` 这条 L0 路径读走的东西比擦盘更多，而且事后审计仍然回答不了"那次放行到底有没有人点过头"——本轮审计日志 40 条记录里，`denied` 依然是 **0**。
