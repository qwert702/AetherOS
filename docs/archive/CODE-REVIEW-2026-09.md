## 2. 跨轮安全教训（结构性，值得复用）

1. **逐分支手写的权限检查必然漏。** 第一轮的 init IPC、第四轮的剪贴板，都是"同一份代码里，权限模型对工具调用生效、对新入口不生效"。修法不是再补一个 `if`，而是**把"每个 `Request` 变体都必须过闸门"写成测试**（`request_variants_are_gated`）。
2. **"看起来做了" ≠ "真的做了"。** 三处同型：审计失败 `let _ =`（有承诺、无告警）；`logtee` 只在打开时查大小（对连续运行数周的服务等于没上限）；`essential: true` 定义了但无读取点。**每一个都通过了 code review，因为"代码看起来是对的"。**
3. **证据链缺陷比功能缺陷更危险。** 归档图过期 → "像素级零回归"的结论站不住 → 之后**所有**基于该图的回归都不可信。审查的基线本身也需要被审。
4. **令牌/密钥不绑定身份就等于没有。** "一次性令牌"只防"模型"不防"任何能连上端口的进程"；而**验收脚本曾把这个缺陷当作正确行为固化**——测试通过不代表行为正确。
5. **白名单 > 黑名单。** 黑名单永远漏（符号链接、大小写、`..` 回绕）。`resolve_readable()` 先 `canonicalize` 再校验，顺序不能反。
6. **分级语义必须与操作语义一致。** 写操作标成 L0"只读"、读（L1）比写（L0）级别高——这种错误不会立刻爆炸，但会在将来接上反向同步时变成 P1。
7. **"用户拒绝了"必须是系统里存在的事实。** `Denied` 不可达 + 拒绝不回传 + 审计不区分来源 → 事后无法回答"那次放行到底有没有人点过头"。**审计的价值不在于记录得多，而在于能区分。**

## 4. 已钉住的边界（改代码时不要无意打破）

### 4.1 VT 解析器的索引运算全部有界（逐条验算，第四轮 §3.1）

终端解析器处理**完全不可信的输入**（PTY 输出的任意字节，包括 `cat /dev/urandom`），
而 `compositor` 是 `essential: true` —— **一次 panic 就等于桌面永久死掉**。

| 位置 | 运算 | 边界结论 |
|---|---|---|
| `put_char` | `cur_y*cols+cur_x`、`idx+1` | `cur_x ≤ cols-1`（已夹取）；`width==2` 时前置条件保证 `cur_x+2 ≤ cols` → 安全 |
| `scroll_up` | `copy_within(n*cols.., 0)` | `n ≤ rows` → `n*cols ≤ len` → 安全 |
| `reverse_index` | `rows - 1` | `Screen::new`/`resize` 均 `rows.max(1)` → 无下溢 |
| `dispatch_csi` L/M/P/X | 多处 `copy_within` + 索引 | 每处 `n` 都先 `.min(...)`，src/dest 长度相等且上界 ≤ `len` → 安全 |
| `erase_display` / `erase_line` | `cur_y*cols+cur_x` | `cur_x ≤ cols-1`、`cur_y ≤ rows-1` → 安全 |
| `param()` | `v as usize`（`v` 是 `u16`） | 解析处 `v.min(65535) as u16` → 64 位下 `cur_y + n` 不溢出 |

**结论：未发现可被 PTY 输出触发的越界 panic。** 渲染侧另有双重夹取。

### 4.2 AI 的 Action 通道无法驱动终端（第四轮 §3.2）

`compositor` 以 root 运行、PTY 直接 `exec /bin/sh` → **"能往 PTY 写字节" == "能在 root shell 里执行任意命令"**。
检查 `apply_action`：AI 的 `Action` 通道**只支持三个动作** —— `layout_set` / `open_app` / `close_active`，其余一律忽略；
**没有任何**向 `term.write()` / PTY 写入的路径（`term.rs` 的 `write()` 只被键盘输入和粘贴调用）。

> **AI（或提示注入）无法通过 Action 通道在终端里执行命令。** 它能做的最多是"打开一个终端窗口"。
> 这条边界是新增 PTY 之后**最容易被无意打破**的地方（例如将来加一个"AI 帮你跑条命令"的 action）——
> 建议在 `apply_action` 上留注释钉死。

### 4.3 其它已确认的正面结论

- **PTY 用正确的 fork 方式**：`Command + pre_exec` 而非手写 `fork`（多线程进程 fork 后只能调 async-signal-safe 函数）；`setsid` + `TIOCSCTTY` 顺序正确；用 `ptsname_r` 而非 `ptsname`（避免静态缓冲竞态）；`Drop` 里 `SIGHUP` + `kill` + `wait` 三重兜底防孤儿。
- **明亮模式渲染确定性可复现**：当前二进制重新出图与归档图**逐像素 0 差异**（884520 像素）→ 软件光栅化管线是确定性的（除时钟与 AI 光标相位），归档图可作回归基线。
- **救援模式从"假死"变成"有出路"**：`loop { sleep(3600) }` → `rescue_console()`，打印**可操作的原因**、给排查路径、开 `/dev/console` shell。
- **协议扩展的向后兼容做得干净**：`approval` / `channel` / `restart` / `essential` 均 `#[serde(default)]`，两个方向（新收新 / 新收旧）都有测试。
