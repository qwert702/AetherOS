## 0. 为什么用假端点，而不是直接接真模型

0.7 的验收目标是"模糊指令 → 工具 → 桌面动作全链路"。这条链上有两层不确定性：

| 层 | 不确定性 | 用假端点能否覆盖 |
|---|---|---|
| **协议层** | aetherd 期望的 `tool_calls` 结构、`tool_call_id` 配对、路由决策、敏感上下文处理 | ✅ 完全覆盖 |
| **模型层** | 真实厂商在 `tool_calls` 结构 / 并行调用 / `finish_reason` 上的差异 | ❌ 覆盖不了 |

**先锁协议层再上真模型，是为了让真模型出问题时能立刻区分"是协议写错了"还是"是这家模型的格式不同"。** 如果一上来就接真模型，两种失败长得一模一样。

假端点的另一个好处：它能把**收到的 `messages` 原样落盘** —— 这是"内容是否离机"唯一可靠的证据来源（源码推断只能得到"应该不会"）。

## 2. 场景 D（★ 核心证据）

**这是 P0-4b（"读到的文件内容不上云"）的完整证明。** 场景设计：

1. 输入 `分析一下这台机器的磁盘占用` —— 含复杂信号「分析」→ 第 1 轮**路由到 Cloud**
2. 假**云端**端点返回 `tool_calls: read_file(<canary 文件>)`（模拟"任务已上云，模型要求读本地文件"）
3. aetherd 执行工具，读到 canary → `sensitive_context = true`
4. 第 2 轮：**被强制拉回 Local**

### 路由轨迹（aetherd stderr）

```
[aetherd] 通道: Cloud · 模型: mock-cloud      ← 第 1 轮：复杂任务上云
[aetherd] 通道: Local · 模型: mock-local      ← 第 2 轮：读到文件后被拉回
```

### 云端端点收到的 payload（第 1 轮，原样摘录）

```
[cloud #1] model=mock-cloud
  system: '你是 Aether，AetherOS 操作系统的 AI 中枢。你可以调用工具查询和操作这台电脑…'
  user: '分析一下这台机器的磁盘占用'
  含 canary: False
```

### 本地端点收到的 payload（第 2 轮，原样摘录）

```
[local #1] model=mock-local
  system: '你是 Aether，AetherOS 操作系统的 AI 中枢。你可以调用工具查询和操作这台电脑…'
  user: '分析一下这台机器的磁盘占用'
  assistant +tool_calls: ''
  tool: '机密内容 CANARY-SECRET-9F3A2B\r\n用于验证「读到的文件内容不上云」。\r\n'
  含 canary: True
```

### 断言

| # | 断言 | 结果 |
|---|---|---|
| D1 | 第 1 轮路由到 Cloud（复杂信号生效） | ✅ |
| D2 | **第 2 轮被拉回 Local（敏感上下文生效）** | ✅ |
| D3 | 云端只收到 1 次请求 | ✅ `cloud 1 次` |
| D4 | 本地收到 1 次请求（第 2 轮） | ✅ `local 1 次` |
| D5 | 云端 payload 不含 canary | ✅ |
| D6 | **本地 payload 含 canary** | ✅ |
| D7 | 最终回答来自 Local | ✅ `[local] 我看了一下，一切正常。` |

### 为什么 D5 和 D6 必须成对

- **只有 D5**（云端没 canary）不足以说明问题 —— 也可能是因为**工具压根没执行**。
- **D6 是必要的对照**：它证明 `read_file` **真的读了**，canary 真的进了上下文。有了 D6，D5 才有意义。
- D3 + D4（云端 1 次、本地 1 次）进一步把"拉回"这件事量化：**不是"一直本地"，而是"第 1 轮确实上云了，第 2 轮才被拦住"**。

> **这正是 P0-4b 要防的场景**：旧实现用 `history_len >= 6` 当复杂度信号，每轮工具调用给消息表 +2 条 —— 两次工具调用之后的第 3 轮必然上云，把前面读到的文件内容整体带走。现在改为只看**内容敏感度**，一旦上下文里进了文件内容就强制本地，无论对话多长、任务多"复杂"。

## 3. 场景 A · 工具链闭环

**输入**：`帮我看一下机器上都有什么`（刻意挑短、无隐私关键词、无复杂信号）

| # | 断言 | 结果 |
|---|---|---|
| A1 | 工具链闭环（本地端点收到 2 轮：`tool_calls` + 最终回答） | ✅ `local 收到 2 次` |
| A2 | canary 确实被读进了上下文 | ✅ |
| A3 | 云端端点一次都没被调用 | ✅ `cloud 收到 0 次` |
| A4 | 云端 payload 里没有 canary | ✅ `cloud payload 长度 2`（即 `[]`） |
| A5 | 两轮路由都是 Local | ✅ |
| A6 | 最终回答来自本地端点 | ✅ `[local] 我看了一下，一切正常。` |

**闭环链路**：`Chat` → 假端点返回 `tool_calls` → aetherd 解析 `function.name` / `function.arguments` → `tools::execute` → 补一条 `role=tool` 消息（带 `tool_call_id`）→ 第 2 轮请求 → 最终回答 → `ChatChunk{done:true, channel:"local"}`。

> **A4 的强度说明**：A4 成立其实是 A3 的推论（云端零调用 ⇒ 云端 payload 为空）。**场景 D 才是强形式** —— 那里云端确实收到了请求，而 canary 只在本地出现。

## 5. 失败路径

### C3 · L2+ 工具被触发时中断，而不是把错误喂回模型

**输入**：`清理一下磁盘`；假端点返回 `tool_calls: install_disk(/dev/vda)`

| # | 断言 | 结果 |
|---|---|---|
| C3a | 返回 `needs_confirmation` 而非把错误喂回模型 | ✅ `['needs_confirmation', 'chat_chunk']` |
| C3b | **只请求了一轮就中断** | ✅ `local 收到 1 次` |
| C3c | 确认请求带等级与回显目标 | ✅ `level=3 echo_required=/dev/vda` |

**C3b 是这条的关键**：如果 aetherd 把"需要确认"当成普通工具结果喂回模型，模型会**编造一个"已执行"的回答** —— 用户以为磁盘被清理了，实际什么都没发生。现在它中断本轮 agent，把结构化的 `NeedsConfirmation` 上抛给 UI。**`local 收到 1 次`（而不是 2 次）就是"没有继续下一轮"的直接证据。**

### C2 · 未配置云端时，复杂任务降级到本地

不设 `AETHER_API_KEY` 启动，输入 `分析一下这台机器的磁盘占用`：

| # | 断言 | 结果 |
|---|---|---|
| C2a | 降级到 Local | ✅ |
| C2b | 本地端点被调用且给出回答 | ✅ |

### C1 · 本地端点不可达时，路由到云端

关掉假 local 端点后启动，输入 `你好`：

| # | 断言 | 结果 |
|---|---|---|
| C1a | 本地探活失败 → 路由到 Cloud | ✅ `[aetherd] 通道: Cloud · 模型: mock-cloud` |
| C1b | 云端端点被调用 | ✅ `cloud 收到 1 次` |

**探活机制**：`agent_run` 开头对 `{local_base}/v1/models` 做一次 2 秒超时的 GET；失败则 `local_available = false`，路由第 5 条把它送去云端。假端点必须实现这个 `GET /v1/models`，否则本地通道会被误判为不可用。

## 6. 未验证：真模型

**这一层本轮没有验证，因为需要外部资源。** 具体缺口：

| 未验证项 | 为什么假端点覆盖不了 |
|---|---|
| 真实厂商的 `tool_calls` 结构差异 | 假端点返回的是**我构造的**标准 OpenAI 格式。真实模型可能在 `arguments` 的编码（字符串 vs 对象）、`id` 的生成、`content` 是否 `null` 上有出入 |
| 并行工具调用（一次返回多个 `tool_calls`） | 代码里 `calls` 是数组且逐个处理，逻辑上支持，但**未实测** |
| `finish_reason` 的取值差异 | 代码目前不看 `finish_reason`（只看 `tool_calls` 是否存在），所以风险低，但未验证 |
| 超时与拒答 | 120 秒超时（`llm.rs:46`）与拒答文本的处理未实测 |
| 多轮真实对话的上下文长度 | 未验证 |

### 接真模型需要什么

任一即可：

1. **本地 Ollama**：`AETHER_LOCAL_URL`（默认 `http://127.0.0.1:11434/v1`）+ `AETHER_LOCAL_MODEL`（默认 `qwen2.5:7b`）。**这是最省事的路径 —— 不需要 API Key，且顺带验证了"本地优先"的设计意图。**
2. **云端 OpenAI 兼容端点**：`AETHER_API_KEY` + `AETHER_API_BASE` + `AETHER_MODEL`（默认 `glm-4-flash`）。

跑通后需要检查的三件事：
- 模型是否**真的**按 `tools` 数组调用工具（而不是用自然语言描述"我建议你调用 read_file"）；
- `tool_call_id` 是否被原样回传（不匹配会导致下一轮 400）；
- 最终回答是否基于工具结果（而不是编造）。

### 6.1 接真模型：三步 + 排障（2026-09-29 补）

**第 1 步 · 配端点**（也可落盘：`aetherd config --api-key … --cloud-base …`；
Linux 写 `/etc/aether/model.json`，权限 0600；开发机写 `%TEMP%/aether-model.json`）：

```bash
# 本地 Ollama：最省事，不需要 Key，且顺带验证"本地优先"的设计意图
export AETHER_LOCAL_URL=http://127.0.0.1:11434/v1
export AETHER_LOCAL_MODEL=qwen2.5:7b

# 或云端 OpenAI 兼容端点（含自建网关；Key 不要写进仓库，也不要写进任何文档）
export AETHER_API_KEY=<你的 Key>
export AETHER_API_BASE=https://<网关>/v1
export AETHER_MODEL=<模型名>
```

**第 2 步 · 先确认通道**：

```bash
cargo run -p aetherd -- config --show                        # Key 只显示末 4 位
cargo run -p aetherd -- chat "现在几点"                      # 离线意图：不该打模型
cargo run -p aetherd -- chat "看看系统还剩多少内存，用一句话总结"   # 必须走模型 + 工具
```

**第 3 步 · 排障：错误信息里就有答案**

`llm.rs` 从 2026-09-29 起在非 2xx 时**把服务器正文带进错误信息**（旧实现只报状态码，
接真模型时无从下手）。对照表：

| 症状 | 含义 |
|---|---|
| `HTTP 401；服务器返回: {"error":{"message":"invalid api key"}}` | Key 错 / 过期 / 没带上 |
| `HTTP 404；…` | **Base URL 少写或多写了 `/v1`**（最常见） |
| `HTTP 429；…` | 被限流：退避或换模型 |
| `HTTP 502 / 504`，正文是 HTML | 自建网关挂了，不是模型的问题 |
| `LLM 响应不是 JSON（可能被网关拦截）… 正文开头: <html>` | 请求打到了登录页/门户页 → Base URL 指错 |
| 连接被拒 / 超时 | 本地 Ollama 没起（`ollama serve`）、端口或防火墙 |

这些分支有回归测试守着（本地假端点，不联网）：`cargo test -p aetherd --offline llm::`

## 8. 结论

1. **协议层已锁死**：agent 循环的完整闭环（路由 → LLM → 工具 → 回喂 → 回答）在真实 IPC 下跑通，21 项断言全过。

3. **L2+ 的中断语义正确**：确认请求不会退化成"喂给模型的普通错误"（那会让模型编造已执行的回答）。

5. **下一步**：接一个真实模型（本地 Ollama 最省事），验证 §6 列出的五项。

## 9. 复现方法

本次验证脚本用后即删（项目约定：临时脚本不污染仓库）。核心结构如下，需要时按此重建：

1. `ThreadingHTTPServer` 起两个端点，各实现 `GET /v1/models`（200）与 `POST /v1/chat/completions`；
2. `POST` 处理器把收到的 body **原样存进内存列表**，再按"上下文里有没有 `role=tool` 消息"决定返回 `tool_calls` 还是最终回答；
3. aetherd 用 `subprocess.Popen([AETHERD, "serve"])` 起，环境变量指向两个假端点；
4. 通过 IPC 发 `{"type":"chat","payload":{...}}`，读响应到 `done`；
5. 断言分三类：**路由轨迹**（aetherd stderr 的「通道:」行）、**端点调用次数**、**payload 内容**（canary 是否出现）。
