# ADR：DRM/KMS 与 GPU 加速路线（G2）

- 状态：**接受（带放弃条件的 spike 决策）**
- 日期：2026-11-21
- 相关：`aether-compositor` 显示路径、G1（Wayland `SCM_RIGHTS`）、G3（damage tracking）、G4（多显示器）、M9 真机验证
- 对标：[后续发展计划（NEXT-PLAN）-2026-10-31](报告/后续发展计划（NEXT-PLAN）-2026-10-31.md) §4.2 G2、[路线图与已知缺口（ROADMAP）-2026-09-05](路线图与已知缺口（ROADMAP）-2026-09-05.md) M1/M3 备注

## 背景

当前桌面画面走 **DRM → fbdev → 软件光栅化** 上屏：合成器在内存缓冲里完成全部绘制，再经 fbdev 帧缓冲输出；没有 Mesa/GBM/EGL 路径，也没有现成合成器宿主。这一事实在路线图 M1 备注与缺口清单 §3.8 中均有记录：

- [功能缺口清单（FEATURE-GAPS）-2026-10-02](报告/功能缺口清单（FEATURE-GAPS）-2026-10-02.md) §3.8：渲染走 `fbdev.rs` / `vt.rs` 单屏路径，真实 GPU 加速在当前代码下不适用；
- [项目进度复盘（STATUS）-2026-11-13](报告/项目进度复盘（STATUS）-2026-11-13.md) 第二节：图形栈（GPU/Wayland）是当前三大瓶颈之一；
- 性能基线：现有帧预算按 **30fps / 33.3 ms** 设定（`scripts/bench-gate.py`），release 构建 P99 ≈ 21.4 ms（FEATURE-GAPS §4.2）。

已有的 Wayland 自研 spike（W1–W4 协议层，W5 的 `SCM_RIGHTS` fd 收包未做，见 ROADMAP「生产力化 Phase 0/1/2 收口」节）属于协议层副产品，**不构成**显示后端结论。

## 备选方案

### 方案 A：维持 fbdev 软件光栅

| 维度 | 评估 |
|---|---|
| 成本 | 最低。现有路径在 QEMU/VBox/VMware 已闭环，无需新增系统库与交叉编译链 |
| 收益 | 零迁移风险；Windows 预览路径与 57 档像素基线不受影响 |
| 风险 | 真显卡上无法利用硬件加速；高分屏/高刷/第三方 Wayland 客户端长期不可达；软件光栅的帧时间随分辨率与界面复杂度线性上涨 |
| 依赖 | 无新增；继续依赖内核 fbdev 仿真层 |
| 判据 | 软件路径在真机 1080p 下帧时间稳定在 33.3 ms 预算内，且没有第三方客户端上屏的硬需求 |

### 方案 B：Mesa + DRM/KMS + GBM/EGL 硬件加速（分两步走）

| 维度 | 评估 |
|---|---|
| 成本 | 中高。第一步只换**显示出口**（fbdev → KMS modeset + dumb/GBM buffer 上屏），绘制仍走现有软件光栅；第二步才评估 EGL/GL 着色与硬件合成。Buildroot 外部树需引入 `libdrm`、`mesa`（按显卡栈裁剪），musl 交叉编译需要在构建机实测 |
| 收益 | 拿到 KMS 多 connector/modeset 能力（G4 多显示器的前置）；为 Wayland 客户端、damage tracking、HiDPI 与硬件合成留出地基；真机帧时间有下降空间 |
| 风险 | ① 交叉编译依赖链在 musl/Buildroot 下可能卡住；② 真显卡驱动覆盖未知（Intel/AMD/集显/ARM 各有差异）；③ 一步到位上 EGL 会把显示出口风险与渲染重写风险叠加，难以回退 |
| 依赖 | 一台可接真显卡的物理机；内核 `CONFIG_DRM`/对应驱动确认；G1 协议层不阻塞显示出口 spike，但真客户端上屏在其后 |
| 判据 | 见下文「决策」中的 spike 验收判据；达不到即回退 A |

### 方案 C：放弃自研合成器，改用现成宿主（smithay / wlroots）

| 维度 | 评估 |
|---|---|
| 成本 | 最高。现有窗口表、布局引擎、命中表、AI Action 通道、像素门禁全部要迁移到宿主的合成模型上；等于推翻 M0–M6 的桌面层 |
| 收益 | 直接获得成熟的输入/输出/客户端协议栈，长期生态成本低 |
| 风险 | 与项目「自研 Rust 用户态」的身份冲突；迁移期现有 794 项测试与 57 档像素基线失去保护；单人维护下迁移失控概率高 |
| 依赖 | 宿主框架的 Rust 维护状态、交叉编译可行性；团队对宿主抽象的掌握程度 |
| 判据 | 仅当 B 路线被证伪，且「第三方 Wayland 客户端可用」成为发布前不可让步的硬目标时，才重新立项评估 |

## 决策

**先做方案 B 的受控 spike，范围严格限定在「显示出口切换」，不做渲染重写；spike 周期 2 周（估算口径沿用 NEXT-PLAN G2 的 1 周基线，留出真机与交叉编译缓冲）。到期达不到验收判据即回退方案 A；方案 C 本轮不切换，仅作为 B 失败后的再评估对象。**

### Spike 范围（只做这些）

1. 在 Linux 侧打开 DRM 主节点，完成一次 KMS modeset（connector → crtc → mode）；
2. 把现有软件光栅产出的帧缓冲（不重写绘制代码）经 dumb buffer 或 GBM buffer 提交到 KMS 平面上屏；
3. 保留 fbdev 路径作为编译期/运行期可回退分支；Windows 预览路径与 `--shot` 像素管线**不动**；
4. 在至少一台真显卡物理机上记录 connector、mode、帧时间与掉帧数据；
5. 产出一份结论记录：依赖是否在 musl 交叉编译通过、哪类显卡可上屏、第二步（EGL/硬件合成）是否值得继续。

### 验收判据（可判定）

- **上屏**：真显卡（非 VMware/QEMU 虚拟显卡）上完成 modeset，现有桌面帧缓冲真实显示，有截图/串口日志证据；
- **帧率**：1080p 典型桌面场景（开窗、滚动、切换虚拟桌面）连续 10 分钟，P99 帧时间 **< 16.7 ms**（60fps 预算），掉帧率 **< 1%**；若该硬件上限只能到 30fps，则 P99 **< 33.3 ms** 且必须如实记录硬件上限，不得按 60fps 报喜；
- **不回归**：`cargo test --workspace --locked` 全绿；Windows 预览与 57 档像素门禁 `shot-diff.py verify` 零差异；现有 fbdev 分支在 spike 失败时可直接切回；
- **依赖可构建**：`libdrm`（及第二步所需的 Mesa 裁剪包）在 Buildroot/musl 交叉编译链下能产出镜像，或明确记录卡点。

### 放弃条件（回退方案 A）

出现以下任一情况，spike 终止并回退 fbdev 软件光栅：

1. 2 周内无法在真显卡上完成一次 modeset 并把现有帧缓冲上屏；
2. 交叉编译依赖链在构建机上不可解，且没有裁剪替代；
3. 真机帧时间达不到 33.3 ms 预算，且定位为 KMS 路径本身的开销而非可优化项；
4. spike 开始侵蚀现有渲染/命中表代码，导致像素门禁或测试基线无法保持。

回退后的状态：文档与界面继续如实标注「软件光栅、无 GPU 加速」；G3 damage tracking 与 G4 多显示器在 fbdev 路径上按各自 ADR 的边界推进。

## 理由

1. **风险拆层**：显示出口（fbdev→KMS）与渲染加速（软件→EGL/GL）是两件事。先只换出口，失败时回退面小；一步上 EGL 会让两类风险叠加，违背项目「可逆优先、失败可判」的既有做法（参考 [aether-shell 归属 ADR](架构决策（ADR）-aether-shell归属-2026-11-13.md) 的取舍口径）。
2. **前置价值独立成立**：即使最终不做硬件合成，KMS 也是 G4 多显示器/旋转的必要地基；spike 拿到的 connector/mode 枚举结论不会白费。
3. **方案 C 时机不对**：当前是单人维护、alpha 阶段，桌面层测试与像素基线是主要安全网；此时换宿主等于自拆安全网。C 的触发条件必须由硬需求驱动，而不是技术偏好。
4. **与既有计划对齐**：NEXT-PLAN §4.2 已把 G2 定为「决策记录 + spike，明确继续 Mesa / 维持 fbdev / 放弃的判据与结论」，本 ADR 给出的正是这套判据。

## 后果

- **若 spike 通过**：第二步再立 ADR 评估 EGL/GBM 硬件合成与 damage tracking（G3）；KMS 抽象层作为 G4 多显示器改造的输入；
- **若 spike 回退**：fbdev 路径保留为唯一显示后端；性能目标继续按 30fps / 33.3 ms 预算管理，不在对外材料中宣称 GPU 加速或高刷支持；
- 无论哪条路径，G1（Wayland `SCM_RIGHTS` 收包）与本路线并行推进，互不阻塞；
- 新增的系统库与显卡支持情况必须进入硬件矩阵三态表（已验证 / 不适用 / 未验证），不得留空白。

## 什么条件下重新评估

1. 真显卡物理机到位并完成 RUNBOOK 显示类项目后，软件路径帧时间数据与本 ADR 判据出现明显偏差；
2. 第三方 Wayland 客户端上屏成为 v0.2 发布前的硬目标；
3. Buildroot/musl 交叉编译环境变化，使方案 B 第二步（EGL）或方案 C 的依赖可行性改变；
4. 硬件矩阵覆盖到第二类显卡后，KMS 驱动覆盖结论需要更新。
