## 一、现状：单点维护

- [项目进度复盘（STATUS）-2026-11-13](项目进度复盘（STATUS）-2026-11-13.md) 第五节如实记录：**516 commits 绝大多数来自同一作者**；仓库 `CODEOWNERS` 当前也只有单一 owner。
- 风险不只在代码：发布账号、构建机访问、更新签名私钥、站点部署都集中在同一人手上。任一情况（离岗、设备损坏、凭据丢失、安全事件）都会让项目无法发版或无法响应漏洞。
- 本文件不改变「当前只有一位活跃维护者」的事实；目标是在不假设第二位立即到位的前提下，把交接清单、权限边界与应急路径写清楚。

## 二、第二维护者职责清单

第二维护者（co-maintainer）按职责域分担，不要求全栈一人通吃，但每个域都要有书面交接与可复跑命令：

| 职责域 | 具体内容 | 验收方式 |
|---|---|---|
| 代码评审 | 审 PR：测试是否补齐、负向用例是否存在、像素门禁与全量门禁结果、是否引入新 unwrap/告警/依赖 | 评审记录留 PR；`cargo test --workspace --locked`、`scripts/gates.py` 结果可复跑 |
| 发布执行 | 按 RELEASE-POLICY 第四节 checklist 逐项执行：构建、校验、签名打包、上传资产、回填 `release.json`、部署站点、健康检查 | 一次完整 beta 发布由第二维护者独立跑通，执行人/复核人留痕 |
| 文档与事实同步 | 行数/测试数/文件数只取权威来源；证据归档 `docs/证据/`；STATUS/路线图条目及时销账；未验证项如实标注 | `doc-numbers-check.py`、`check-links.py`、`site-health-check.py` 通过 |
| 安全响应 | 按 [SECURITY.md](../../SECURITY.md) 私密通道分诊；依赖审计（`cargo audit`）、权限闸门与审计日志复查；可疑凭据上报 | 安全报告有受理记录与处置结论；不公开贴细节 |
| 发布链路维护 | 维护 keygen / mkupdate / publish / readiness / site-health 等脚本与契约检查；脚本改动补 `--selftest` 或负向对照 | 脚本自检通过；更新契约 `update-contract-check.py` 守门 |

## 三、所需权限与密钥保管

> 原则沿用 DEPLOY-ACCESS：不直连 root、不把私钥内容发到聊天、不在仓库保存密码；下表只列权限类别与保管要求，敏感值不写入本文档。

| 权限类别 | 内容 | 保管要求 |
|---|---|---|
| 仓库写权限 | 推送分支、合入 `main`、管理 Release 资产；`CODEOWNERS` 评审权限 | 第二位维护者以自己的 GitHub 账号授权，不共用主账号 |
| VPS 部署权限 | `aether-deploy` 非 root 账号 + 公钥 + `sudo -n` 白名单；站点目录 `/var/www/aether.cbnac.com/` 与更新源 `/var/www/aether.cbnac.com/updates/` | 禁止 root 直连；公钥可公开，私钥留在各人本机；账号/权限变更登记回 DEPLOY-ACCESS |
| 构建机访问 | Linux Buildroot 构建机 SSH（重建 ISO、跑 musl 交叉检查） | 密钥不入库；交接时换公钥，不复制私钥文件 |
| 更新签名密钥 | Ed25519 更新清单签名私钥（`scripts/update-keygen.py` 生成，默认仓库外 `~/.aether/update-signing-key.pem`，0600）；公钥入库 `aetherd/keys/update_pubkey.bin` | **私钥不得以明文共享、不入库、不进聊天/文档**。双人方案二选一：① 两人各持一份独立加密备份（口令各自保管）；② 一人持有私钥，另一人持有离线封存的备份信封。私钥丢失 = 无法再签新更新；公钥替换后旧客户端不再接受新清单，轮换必须走发布流程 |
| LLM 网关凭据 | 自建网关 Base URL + 临时 API Key，走环境变量 | 不写进系统镜像、不入库；过期即失效，不长期留存 |
| 应急访问记录 | 上述账号/密钥的存放位置、重置方式、联系人 | 登记在 DEPLOY-ACCESS 与本文配套清单；位置可查，内容不落明文 |

## 四、发布交接步骤（双人复核 checklist）

每次 stable（以及涉及签名/部署的 beta）发布按「执行人 + 复核人」双人进行：

**执行人**先完成 RELEASE-POLICY 第四节全部 11 项 checklist，并产出可复跑记录（命令、退出码、关键输出）。

**复核人**独立复核以下条目，不默认信任执行人自述：

1. 测试与全量门禁结果真实可复跑；像素差异为 0 或有批准记录；
2. `release-readiness.py` 输出全绿；ISO 字节数 / SHA256 与下载回来的资产逐字节一致；
3. 更新清单签名验证通过：公钥指纹与入库 `aetherd/keys/update_pubkey.bin` 一致；签名私钥操作由持有人本人完成，复核人不接触明文私钥；
4. `site-health-check.py` 本地/线上一致，安全响应头在位；
5. 回滚步骤可执行：上一版 ISO 与哈希仍可下载，keepvar 与文件级回滚路径已演练；
6. 撤回流程就绪：更新源下架、`release.json` 回滚、Release 标记 prerelease 的操作路径明确；
7. 发布说明写明兼容范围、已知边界、未验证项；
8. 执行人与复核人在 Release 说明或发布审计记录中分别署名；意见不一致时不发版，先回到 checklist 定位问题。

## 五、离职 / 失联应急流程

### 5.1 在岗离职（可计划交接）

1. 冻结新权限授予；盘点第三节全部权限类别，逐项列出持有情况；
2. 轮换该人员持有的 SSH 公钥/部署密钥；确认签名私钥已移交加密备份或重新生成密钥对；
3. 仓库成员移除、`CODEOWNERS` 更新；VPS/构建机账号禁用；
4. 交接文档、证据目录、未决 issue 与安全分诊记录逐项过手；
5. 变更结果登记回 DEPLOY-ACCESS 与本文档。

### 5.2 失联 / 不可用

1. **可发布范围**：第二维护者持有的备份足以执行 beta 发布与缺陷修复；stable 全量推送等待主维护者恢复，或达到下文应急条件后由双人（或剩余维护者 + 一位可信评审）共同判定放行。
2. **密钥应急**：签名私钥无法取得时，不允许绕过验签发更新；按密钥轮换流程生成新密钥对、公告旧清单失效边界，并在镜像/站点侧完成公钥替换。
3. **基础设施重置**：依据 DEPLOY-ACCESS 清单，由可接触 VPS/构建机的人员重置部署账号与公钥；失联人员的密钥从 `authorized_keys` 与 sudoers 中移除。
4. **时限约定**：超过 90 天无法联系，启动正式权限转移：仓库 owner 变更流程、密钥全量轮换、本文档重写。
5. **安全事件优先**：若失联伴随密钥泄露或仓库异常，先走 [SECURITY.md](../../SECURITY.md) 通道：停签、撤资产、轮换凭据，再谈恢复发布。

### 5.3 密钥泄露判定

私钥怀疑泄露即视为泄露：停止用该私钥签新清单 → 轮换密钥对 → 评估已签清单是否需要撤回 → 在发布说明中写明影响版本与处置。

## 六、30 / 60 / 90 天落地计划

> 时间为估算，不是承诺；每一档完成判据可核对，未完成保持「未完成」标注。

| 阶段 | 目标 | 交付物 / 判据 |
|---|---|---|
| **30 天** | 清单化，摸清单点 | ① 第三节权限与凭据类别全部归档到 DEPLOY-ACCESS（只记位置与重置方式，不记明文）；② 识别出所有单人持有的凭据；③ 第二维护者旁观一次完整 beta 发布，记录每一步命令与输出；④ 本文档经评审并进入文档索引 |
| **60 天** | 第二维护者可独立跑发布流程 | ① 第二维护者独立执行一遍发布 checklist（签名私钥操作仍由持有人完成）；② 独立完成一次 beta 发布并通过复核；③ 签名密钥双备份/离线封存方案落地，备份位置登记（内容不登记）；④ 构建机与 VPS 访问对第二维护者验证通过 |
| **90 天** | 双人发布闭环 + 应急演练 | ① 双人复核完成一次正式线发布；② `CODEOWNERS` 补入第二维护者；③ 做一次失联应急演练：复核人在主维护者不参与的情况下走通 hotfix 发布路径；④ 复盘演练卡点，更新本文档与 RELEASE-POLICY |

## 七、什么条件下重新评估

1. 活跃维护者人数变化（新增第三位、或第二维护者退出）；
2. 签名密钥轮换、新增部署目标（新 VPS / 新构建机 / 新发布通道）；
3. 镜像级 OTA 或多用户落地，带来新的发布权限面（见 [镜像级OTA与A-B分区 ADR](../架构决策（ADR）-镜像级OTA与A-B分区-2026-11-21.md)、[多用户与会话 ADR](../架构决策（ADR）-多用户与会话-2026-11-21.md)）；
4. 90 天计划到期复盘时，按实际卡点修订职责清单与应急时限。
