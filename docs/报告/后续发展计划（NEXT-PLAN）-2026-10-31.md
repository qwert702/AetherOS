# AetherOS 后续发展计划（NEXT-PLAN）— 2026-10-31

> 这份计划把当前 `v0.1.1` 与“可日常使用”之间的差距拆成可验收的工作项。
> 它是**工程计划**，不是发布日期承诺；时间估算依赖构建机、物理机和 VPS 权限是否到位。
>
> 当前基线：`main` @ `70e352c` · 52,544 行 Rust / 77 文件 / 7 crate · 793 测试 ·
> 42 门禁 · CI run #91 四 job 全绿 · `cargo audit` 0 漏洞。

## 一、目标与边界

### 1.1 总目标

把 AetherOS 从“虚拟机里能跑、能装真实 Linux 软件的早期系统”推进到
“**可安装、可更新、可日常使用、可被外部开发者验证**的开源桌面操作系统”。

### 1.2 三条主线

| 主线 | 目标 | 完成判据 |
|---|---|---|
| **A. 发布闭环** | 官网、ISO、更新源三者一致且可验证 | 用户从官网下载的 ISO 能在虚拟机装机；更新包能 signed 发布并被 guest 应用 |
| **B. 真机可用** | 从“虚拟机验证”扩大到“物理机验证” | RUNBOOK 45 项在至少两台物理机上有日期、机器、结果与证据 |
| **C. 平台化** | 从“自己写的桌面”变成“能承载第三方应用与长期维护的系统” | Wayland/DRM 路径有结论；应用分发、OTA、代码拆分有明确落地 |

### 1.3 明确不在本计划内（沿用现有边界）

以下项在 `FEATURE-GAPS` 中已判定“有意不做”，除非产品目标改变，否则不排期：

- 重写内核（继续使用 Linux 内核）。
- 镜像级 OTA / A-B 分区（先做文件级更新，镜像级另立专项）。
- 多用户 / 增删用户（先保持单用户 + 密码）。
- 休眠 / 唤醒、蓝牙配对/连接、提交打印作业。
- 多显示器与旋转、跨虚拟空间拖拽。

这些不是“忘了”，而是当前阶段投入产出比不足；重新评估时必须先写新的验收标准。

## 六、每项的“完成”定义

一个工作项只有同时满足以下五条才算完成：

1. 代码/文档已提交到 `main`，有独立提交或 PR；
2. 有可复跑命令或证据文档（不是口头结论）；
3. 相关测试/门禁通过；涉及像素的必须过 `shot-diff.py verify`；
4. 未验证项明确写成“未验证”，不得用“应该可以”替代；
5. 更新 `docs/README.md` 的当前事实或对应证据索引。

## 七、风险与外部依赖

| 风险 | 影响 | 缓解 |
|---|---|---|
| 没有非 root VPS 账号 | 站点无法按安全策略部署 | 创建部署账号 + 公钥；禁止 root 直连 |
| 没有 Linux 构建机 | ISO 无法重建，R2/R3 卡住 | 使用现有 Buildroot 构建机或准备 Ubuntu 24.04 环境 |
| 没有物理机 | H1/H2 无法执行 | 借一台 x86_64 机器；按 RUNBOOK 逐项记录 |
| 没有真实 LLM 网关凭据 | R8 无法执行 | 使用自建网关；不把上游 Key 写进系统 |
| 图形 spike 失控 | 工期不确定 | 按 PHASE3 的放弃条件：2 周不能上屏就回退 fbdev |
| 发布资产/官网再次漂移 | 用户下载到错误哈希 | 每次发布强制跑 `site-health-check` + `release-readiness` |
