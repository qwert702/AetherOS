# ADR：镜像级 OTA 与 A/B 分区（P2）

- 状态：**接受（现阶段不立项；锁定目标架构与前置条件）**
- 日期：2026-11-21

## 背景

### 现行更新机制（代码事实）

当前是**文件级离线更新包**，不是镜像级 OTA：

- `aetherd/src/update.rs`（883 行）：先验签 `update.json.sig`（Ed25519 detached signature），再解析清单、逐文件校 SHA-256，不符整包拒绝；清单白名单前缀为 `/var/apps/`、`/etc/aether/`、`/var/lib/aether/`（`aetherd/src/updater.rs:16`）。
- `aether-init/src/update.rs`（376 行）：启动时按 `apply.list` 暂存表**再核一遍 SHA-256** 才应用；2026-11-14 回滚演练修复了「只校大小、不校哈希」的缺口（文件头注释第 19 行）。
- 系统组件（`/usr/bin/*` 等）**刻意不在文件级白名单内**：这类升级走整机路径——新 ISO + 无人安装 + `--keep-var`（`scripts/mkupdate.py` 文件头说明）。
- 现有签名/发布链路：`scripts/update-keygen.py`（Ed25519 密钥对，私钥不入库）、`scripts/mkupdate.py`（打包）、`scripts/publish-updates.py`（干跑优先，显式 `--apply` 才上传）、`scripts/update-contract-check.py`（清单契约检查）。
- 持久化：磁盘第 2 分区 ext4（卷标 `AETHER`）由 `aether-init` 挂到 `/var`，日志/审计/已装应用跨重启保留（`aether-init/src/persist.rs`；安装器见 `aether-install/src/main.rs:46`）。
- 已验证：QEMU 下两轮 keepvar 升级、一次原地文件级更新、一次文件级回滚均 PASS（[QEMU双次装机-2026-11-14](证据/QEMU双次装机-2026-11-14.md)）；guest 拉取探测包 E2E 见 [更新E2E-2026-11-05](证据/更新E2E-2026-11-05.md)。

### 现状磁盘与引导模型

系统根来自 ISO/initramfs 镜像 dd 到磁盘；MBR 第 2 项追加 ext4 持久分区挂 `/var`（`aether-install/src/main.rs:10`）。**磁盘上没有第二个可写系统槽位**，引导链路也没有「选槽启动 / 失败回退另一槽」的机制。

## 备选方案对比

### 方案 1：维持现行文件级更新（+ 整机换镜像保 `/var`）

| 维度 | 评估 |
|---|---|
| 分区表 / 引导改动 | 无。沿用现 MBR + 持久分区模型；整机升级靠重装 ISO 时 `--keep-var` 复用 `/var` 分区 |
| 签名与回滚边界 | 清单 Ed25519 验签 + 逐文件 SHA-256；回滚是文件级（暂存表恢复），不覆盖已替换的系统组件；整机回滚 = 重装上一版 ISO + keepvar |
| `/var` 保留 | 文件级更新不动 `/var`；整机换镜像由 keepvar 保 ext4 分区（UUID 不变），历史上出现过分区项索引差一导致认不出分区的缺陷，已在 QEMU 两轮升级中复核（见 [T3验证-keepvar保住var-2026-10-17](证据/T3验证-keepvar保住var-2026-10-17.md) 的更正记录） |
| 磁盘占用 | 最低：单系统镜像 + `/var` 分区 |
| 失败恢复路径 | 更新包验签/哈希失败整包拒绝；启动时应用前再校哈希；整机升级失败可回内存态引导（现有安装器 fail-closed 口径） |
| 成本量级 | 已落地，无新增开发成本 |
| 短板 | 系统组件升级必须重装镜像；没有「更新失败自动回退到上一个可启动系统」的槽位级保障；断电发生在整机替换中途需要人工恢复 |

### 方案 2：A/B 双分区整镜像

| 维度 | 评估 |
|---|---|
| 分区表 / 引导改动 | **大**。需要两个等大的可写系统分区（slot A / slot B）+ 共享 `/var` 分区；引导加载器（GRUB/syslinux，按 Buildroot 实际链路选定）必须记录活动槽位、待启动槽位与尝试计数；安装器要从「dd ISO + 追加持久分区」改为「分区表重排 + 双槽落盘」 |
| 签名与回滚边界 | 整镜像或镜像清单走现有 Ed25519 链路扩展：公钥仍入库 `aetherd/keys/`，私钥仍离线保管；签名覆盖镜像哈希与版本号。回滚边界是**槽位级**：引导器在 N 次启动失败后切回另一槽；应用层配置快照（现有快照页）作为补充，不作为槽位回滚的替代品 |
| `/var` 保留 | `/var` 独立于双槽，任何槽位启动都挂同一块持久分区；用户数据与已装应用不参与槽位回滚 |
| 磁盘占用 | 高：两个系统槽位 ≈ 2× 根镜像体积（当前 ISO 约 26.0 MB，根镜像长大之后占用需重新估算）+ `/var` |
| 失败恢复路径 | 下载到非活动槽 → 验签校验 → 切换活动槽 → 引导计数；启动失败超阈值自动回退原槽；最坏情况进入救援控制台（现有 init 救援模式扩展） |
| 成本量级 | **大，数周级专项**：分区表、引导选槽、安装器改造、init 槽位状态机、双槽产物构建、回退计时器与负向测试，缺一不可 |
| 前置条件 | ① 引导链可改造（GRUB/syslinux 配置与分区约定明确）；② 安装器支持分区重排；③ 真机断电/坏槽恢复演练通过；④ 文件级更新与真机 E2E 已稳定（R7 后续复测） |

### 方案 3：差分镜像更新（bsdiff/zstd 整镜像增量）

| 维度 | 评估 |
|---|---|
| 分区表 / 引导改动 | 自身不改变分区模型；但差分要落到某个底座上——要么叠加在 A/B 槽位上，要么仍是整机替换，不构成独立架构 |
| 签名与回滚边界 | 差分包需绑定基版本哈希（只允许从指定旧版差分上来），签名覆盖差分包与解出后的整镜像哈希；基版本不匹配必须整包拒绝 |
| `/var` 保留 | 同方案 2，取决于底座模型 |
| 磁盘占用 | 下载体积小，但落地仍需要整镜像空间；生成器要为每个相邻版本对产出差分，存储与测试矩阵随版本数增长 |
| 失败恢复路径 | 差分解包失败/哈希不符 → 放弃差分，回退整镜像下载；恢复能力不优于底座方案 |
| 成本量级 | 中：差分生成器、基版本匹配校验、补丁应用与负向测试；但**必须先有整镜像底座**，单独做没有意义 |

## 决策

**v0.1 → v0.2 阶段维持方案 1（文件级更新 + 整机换镜像保 `/var`），镜像级 OTA 本轮不立项。若未来立项，目标架构选方案 2（A/B 双分区整镜像），方案 3（差分）作为下载体积优化后置叠加在 A/B 之上；不在现有文件级链路上叠加镜像级修补。**

理由：

1. **前置条件尚未成立**：当前磁盘模型没有可写系统槽位，引导器没有选槽与回退计数；A/B 是分区表 + 引导 + 安装器 + init 的联动改造，不能靠用户态补丁完成。
2. **现有链路刚闭环**：文件级更新、keepvar、文件级回滚在 QEMU 完成演练，真机在线复测仍未做完（STATUS M8 遗留）；此时另起镜像级专项会分散发布闭环资源。
3. **差分不能独立存在**：没有整镜像底座时，差分只是另一种整机替换包，解决不了「坏槽自动回退」这个镜像级 OTA 的核心价值。
4. **与既有边界一致**：NEXT-PLAN §1.3 与 FEATURE-GAPS #41 已把「镜像级 OTA / A-B 分区」列为有意不做、另立专项；本 ADR 把再评估的触发条件写清楚，而不是把缺口遗忘。

### 成本量级与前置条件（立项时核对）

- A/B 专项估算：数周级，含引导选槽、分区重排、安装器改造、init 状态机、双槽构建产物、坏槽/断电负向测试；
- 前置条件清单：
  1. 文件级更新真机在线 E2E 复测通过；
  2. 引导链改造方案明确（GRUB 或 syslinux，选槽配置与备份引导项落地）；
  3. 安装器支持在已有 `/var` 的磁盘上重排系统分区，且 keepvar 不回归；
  4. 磁盘容量目标机型确认能容纳双槽；
  5. 签名密钥轮换与离线保管流程按 [维护交接与双人发布（MAINTAINER-HANDOVER）](报告/维护交接与双人发布（MAINTAINER-HANDOVER）-2026-11-21.md) 就位。

## 后果

- 系统组件升级在 A/B 落地前，继续走「新 ISO + `--keep-var`」路径；更新页与对外材料不得暗示支持在线整机升级；
- 文件级白名单保持收窄（`/var/apps`、`/etc/aether`、`/var/lib/aether`），不借 ADR 名义放宽到 `/usr`；
- 现有签名链路（keygen / mkupdate / publish / contract-check）在 A/B 落地时复用，公钥与验签代码不重写；
- 差分方案只做技术储备记录，不排开发工期。

## 什么条件下重新评估

1. 出现文件级更新无法覆盖、必须在线替换系统组件的真实需求（如内核/系统库升级）；
2. 真机演练证明整机换镜像在断电/中断场景下不可接受，需要槽位级自动回退；
3. 引导链与安装器改造完成，前置条件 1–5 逐项销账；
4. 目标机型磁盘容量确认支持双槽，且根镜像体积增长仍在预算内。
