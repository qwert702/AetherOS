## 2. 安全增补：三个必须在功能之前修的东西

> **状态：✅ 已于 2026-09-28 全部修复并验证** —— 见 `docs/FIX-REPORT-2026-09-28.md`。
> 本节保留原始的缺陷描述，作为决策历史与回归依据。

第四轮审查的发现直接落在 09-27 版的 Phase 2 和 Phase 4 上。**它们不是"额外的技术债"，而是已经写进清单、标了 ✅ 却带病的项。**

### 2.1 【P1】剪贴板 IPC 端点零门槛 —— 2.2 的"完成"是带病的

**位置**：`aetherd/src/server.rs:239-250`

`Request::ClipboardGet` / `ClipboardSet` 既不验密钥、不检查 `is_ui`、也不走 `Gate::judge`，只补了一行 `gate.audit(...)`。

**实测**（同一次 `aetherd serve` 会话，**未注册**连接）：

```
A. 未注册 · clipboard_get   → clipboard_text {'text': ''}
B. 未注册 · clipboard_set   → clipboard_written {'bytes': 15}
C. 未注册 · 回读           → clipboard_text {'text': 'PWNED-BY-UNAUTH'}
E. 未注册 · L3 无令牌       → error code=403 'L2+ 操作（install_disk）必须由已注册的 UI 通道发起'
```

**同一个端点内，权限模型守住了 L3 的危险操作，却没守住用户刚复制的密码。**

**为什么这改变了排期**：09-27 版把 2.2 标为完成，于是 Phase 2 的后续项（2.3 IME、2.4 统一文本交互）会**建立在一个已经漏了的通道上**。2.4 要统一三处文本交互 —— 如果那时剪贴板仍是零门槛，统一的结果是把漏洞铺开。

**处置**：**重开 2.2**，拆成：

| 子项 | 内容 | 量 |
|---|---|---|
| 2.2a | 剪贴板 IPC 纳入权限模型（要求 `is_ui`，或给剪贴板单独定级走 `Gate`） | S |
| 2.2b | 补测试：**枚举 `Request` 全部变体，断言每个"读用户数据或改系统状态"的变体都经过闸门** | S |
| 2.2c | 剪贴板内容加超时清理（当前是进程级 `static`，无生命周期） | S |

> **2.2b 是这次最重要的产出** —— 它不是修一个 bug，而是修**产生这类 bug 的机制**。根因：`handle_request` 的权限检查是**逐分支手写**的，新增 `Request` 变体就多一处可能漏检的入口。用测试把"每个入口都必须过闸门"固化下来，下一个变体就不会重演。

### 2.2 【P2】4.3 日志轮转要重开：安全日志反而没有轮转

**位置**：`aetherd/src/perm.rs:125-135`

```rust
pub fn audit(&self, tool: &str, level: Level, args: &str, verdict: &str) -> std::io::Result<()> {
    ...
    let mut f = std::fs::OpenOptions::new().create(true).append(true).open(&self.audit_path)?;
    writeln!(f, "{ts}\t{level}\t{tool}\t{args}\t{verdict}")
}
```

只 append，**无大小检查、无轮转**。而本轮新增的 `aether-init/src/logtee.rs` 给**服务日志**加了 8MB 运行期轮转（`rotate_in`，带 3 个单测）。

**安全关键的审计日志，反而没有服务日志的保护。**

**放大因素**：所有 `audit()` 调用点都是 `let _ = gate.audit(...)` 忽略返回值。磁盘写满后审计**静默停止**，系统继续正常运行 —— 一个"看起来在工作"的审计系统比一个明显坏掉的更危险。注意 `ai-permissions.md:20` 的书面承诺是"审计写入失败不阻断执行，但错误会显式返回调用方并落 stderr，**不允许静默零留痕**" —— **实现没有兑现这句话**（`let _ =` 就是静默）。

**处置**：重开 4.3，拆成 4.3a（服务日志，已完成）/ **4.3b（审计日志轮转 + 写失败告警）**。把 `rotate_in` 从 `logtee` 提取为共享工具即可。

### 2.3 【P2】剪贴板链路的两个配套问题

| # | 问题 | 位置 | 处置 |
|---|---|---|---|
| a | `clipboard_write` 标为 **L0（只读）**，而 `clipboard_read` 是 L1 —— **读比写级别高，方向反了** | `tools.rs:58` | 提级到 L1。当前**无可利用链**（`sync_clipboard_to_daemon` 只有 compositor→aetherd 单向，AI 写的剪贴板到不了用户粘贴），但一旦接上反向同步就是 P1 |

### ★ 我的建议：把 0.6 / 0.7 提到 Phase 0 的最前面

**理由（这是本文最重要的一条排期意见）**：

整个项目的叙事是"AI 中枢的操作系统"。而**至今没有任何一次真实 LLM 端到端验证** —— roadmap 里这一项从 M4 一直挂到现在。

这构成一个**架构级未知**：`aetherd` 的 agent 循环（`agent_run`）、工具调用格式、L2+ 确认的中断上抛（`NeedsConfirmation` 而非把错误字符串喂回模型）—— 这整条链是**按 OpenAI 兼容协议的假设写的**，但从未与真模型对过。如果真模型的 tool-call 返回格式有出入（不同厂商在 `tool_calls` 结构、并行调用、`finish_reason` 上都有差异），返工范围是 `tools.rs` + `agent_run` + 确认卡片 + 合成器的 `AiEvent` 处理 —— **横跨三个 crate**。

**对比一下优先级**：

| | 0.7 真实 LLM 验证 | 2.3 中文 IME |
|---|---|---|
| 性质 | **地基验证**（验证已有假设是否成立） | 锦上添花（新增能力） |
| 失败代价 | 三个 crate 返工 | 一个模块重做 |
| 依赖 | 无（可立即做） | 0.3（已完成） |
| 当前状态 | 排在 Phase 0 最后 | 排在 Phase 2 中间 |

**IME 晚做一周，用户少打一周中文；真实 LLM 验证晚做一周，可能白写一周的 agent 循环。**

**可复用的做法**：`aetheros-security-review` skill 的 §3.5 记了一套**双假 LLM 端点**方法（`ThreadingHTTPServer` 起两个 OpenAI 兼容端点，把收到的 `messages` 完整落盘，用于证明"内容是否离机"）。0.7 可以直接复用这套脚手架 —— 假端点验证路由与协议格式，真端点验证真实模型。**先用假端点把协议跑通，再接真模型**，这样真模型出问题时能立刻区分"是协议写错了"还是"是这家模型的格式不同"。

### ★ 必须固化的安全边界：AI 不能驱动 PTY

第四轮审查确认（前提：`compositor` 以 **root** 运行、PTY 里 `exec /bin/sh` 即 **root shell**）：

`apply_action`（`main.rs:999-1033`）**只有三个动作** —— `layout_set` / `open_app` / `close_active`，**没有任何向 PTY 写入的路径**。

所以：**AI（或提示注入）无法通过 Action 通道在终端里执行命令。** 它能做的最多是"打开一个终端窗口"，窗口里的命令仍需用户亲自输入。

**这条边界目前是干净的，但它是本轮新增 PTY 之后最容易被无意打破的地方。** 将来任何人想加一个"AI 帮你跑条命令"的 action，都会在一行之内把 root shell 的执行权交给模型。**建议在 `apply_action` 上加一条注释把这个边界钉死**，并在 `ai-permissions.md` 里补一节写明。

我补三条**具体的设计约束**，全部来自第四轮审查的实证：

1. **所有新入口必须走 `Gate::judge`，禁止在 `handle_request` 里手写例外。**

## 8. 六个硬门禁（重新定义）

09-27 版列了六条，但**它们只描述了结果，没有描述机制**。我按本轮审查结论重新定义：

### 门禁 1 · 连续运行 8 小时不崩 —— **需要拆成两条**

| | 内容 |
|---|---|
| 1a | 连续 8 小时无 panic |
| **1b** | **panic 后能自动恢复**，或**证明关键路径无 panic** |

**理由**：`compositor.json` 是 `essential: true` + **`restart: false`**（而 `unit.rs:122` 的默认值是 `true`，只有 compositor 显式关掉了）。所以 **compositor 一次 panic = 桌面永久死掉，需要手动重启整机**。

在这个前提下，"8 小时不崩"是**运气**，不是**设计**。要么给它开 `restart`（并验证重启后桌面状态可恢复），要么把关键路径的 panic 可能性逐个排除（§3 的 0.8）。**两条路选一条，不能不选。**

> ### ✅ 1b 已于 2026-09-28 达成（走的是"开 restart"这条路）
>
> **根因比本文写的更具体**：`restart: false` 不是随手设的，而是 **09-12 按当时的语义**设的 ——
> 原话是"compositor 改 restart:false：**崩溃由 ops 巡检自愈（15s 内），监督器不接管**"。
> 但 09-19 的 P1-3（`a0f1268`"重启策略以服务定义为唯一事实来源"）把 ops 改成
> `if !s.restart { 不冷拉起 }`，于是 `restart: false` 的语义从"**ops 接管**"变成了"**没人接管**"——
> 而 compositor 的配置没有跟着回头核对。**两处代码都自洽，矛盾只存在于两者之间。**
>
> **修法**：`compositor.json` → `restart: true`（init 监督 + ops 冷拉起双通道）。
> 并加了一条不变量测试 `shipped_essential_services_must_be_restartable`
> （`aether-init/src/unit.rs`）：随镜像发布的 `essential: true` 服务必须 `restart: true`，
> 因为"关键、但退出后没人拉起"等价于"关键且必然永久失效"。
>
> **实机验证**（新 ISO + QEMU + QMP 注入键盘）：
> ```
> root login on 'tty1'
> $ killall aether-compositor
> [aether-init] compositor 退出 (code=-1, restarts=0)
> [aether-init] compositor 已重启 (第 1 次)
> aether-compositor: fbdev 1280x800 @32bpp stride=5120 ... 通路=write
> aether-compositor: 字体已加载 /usr/share/fonts/truetype/wqy/wqy-microhei.ttc
> aether-compositor: evdev 输入已接入（3 个设备）
> aether-compositor: 已渲染 1 帧
> ```
> 即：被杀 → init 同一秒发现退出 → 拉起 → 重新初始化显示/字体/输入 → 继续渲染。
>
> **门禁 1 现在两条都达成了**：**1b 走"开 restart"**（2026-09-28，实机 kill 验证），
> **1a 走"实机长跑"**（2026-09-28 21:46 → 09-29 10:30，**连续 12 小时 43 分**，要求 8 小时）。
> 长跑数据：3053 轮巡检，服务退出 0 / 自动重启 0 / panic 0 / 内存告警 0，内存 474/971MB 稳定；
> 原始串口日志存于 `docs/evidence/soak-2026-09-28-12h43m.log.gz`。
> **六个硬门禁至此 6/6 全部达成。**
