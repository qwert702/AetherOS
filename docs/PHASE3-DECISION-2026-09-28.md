- **结论**：**这些项不在本轮实施范围内**，原因不是"没时间"，而是**前置条件不成立**
- **本文交付的是**：3.1 spike 的决策框架（含**放弃条件**）、4.4/4.5 的可行性评估

## 0. 为什么本轮不做，以及为什么这不是偷懒

Phase 3 在 09-27 版里被标为 **XL（月级）**，并且原文就写着"**先做 spike 再排期**"。4.4/4.5 都要求**真实机器**。

本轮的边界是：**能在 Windows 开发机上实现并验证的项**。已完成的 9 项（0.6/0.7/0.8/2.2/2.3/2.4/4.1/4.3b + 第四轮 9 项修复）全部落在这个边界内，每项都有实测证据。

Phase 3 与 4.4/4.5 跨出了这条边界：

| 项 | 跨出边界的原因 |
|---|---|
| 3.1–3.5 | 需要 **Linux 实机**（DRM/KMS、Wayland 协议、GPU）+ 需要先有 spike 结论 |
| 4.4 | 需要 **QEMU/VM** 环境与一个能跑虚拟化的 CI runner |
| 4.5 | 需要**真实分区布局**才能验证备份/还原 |

**把它们草草实现（无法验证）比不做更糟** —— 那会产生"看起来完成了"的假象。这正是第四轮审查里 P1-1 的教训：一个标了 ✅ 但没被验证的项，比一个标 ⬜ 的项危险得多。

## 1. 3.1 Wayland spike 的决策框架

### 1.1 两条路线的对比

| | **A. smithay** | **B. 自研 `wl_display` 子集** |
|---|---|---|
| 成熟度 | 高（Rust 生态主流合成器框架） | 低（要自己实现协议） |
| 依赖链 | wayland-server、calloop、nix、**Mesa（EGL/GBM）** | 仅需 wayland 协议定义 + `wl_shm` |
| 交叉编译到 musl 静态 | **Mesa 是最大风险** —— 它对 musl 静态链接的支持一向很差 | 依赖极少，风险低 |
| 输入 | 通常配 libinput + seatd | **可直接复用现有的 evdev 采集层**（`input.rs`） |
| 工作量 | 中（框架代劳） | 高（协议自己写） |
| 何时该选 | 目标是"跑真实第三方客户端"（Firefox、GTK 应用） | 目标是"自有应用能上屏" |

### 1.2 ★ 我的建议：**先做 B，把 A 作为后续**

理由：

1. **B 避开了最大的坑**。A 路线要交叉编译 Mesa 到 musl 静态 —— 这是整个 Phase 3 里不确定性最高的一环，而它带来的收益（GPU 加速）在 3.3 才需要。先做 A 等于把两个高风险绑在一起。
2. **B 能复用已有资产**。`input.rs` 已经有 evdev 直读后端（真机路径在用），B 路线不需要 libinput/seatd —— 又砍掉两个交叉编译目标。
3. **B 的产出立刻有用**：`wl_shm` 客户端上屏意味着 AetherOS 有了**第一个真实的图形应用协议**，这是从"自研 UI"到"能跑别人的程序"的实质一步。
4. A 路线随时可以接在 B 之后 —— 两者共享 `wl_display` 的核心（协议解析 + 对象表），B 的代码不是白写。

### 1.3 spike 的最小目标（可判定）

> **一个用 `wl_shm` 创建 surface、画一个纯色矩形、并响应 `xdg_shell` 的 map/unmap 的客户端，能在 AetherOS 上显示出来。**

不要求：多客户端、焦点管理、窗口装饰、GPU 加速。

### 1.4 **放弃条件（必须提前写死）**

| 条件 | 处置 |
|---|---|
| 2 周内无法让 `wl_shm` 客户端上屏 | **放弃 Wayland**，维持 fbdev；把时间投到 3.3 的 damage 追踪 |
| `wayland` 协议头/库的交叉编译超过 1 周未打通 | 同上 —— 说明依赖链问题比预期深 |
| 上屏成功但帧率低于当前 fbdev 路径 | 记录数据后**暂停**，先做 3.3 的局部重绘再回来 |

**为什么必须提前写死**：09-27 版已经识别"Wayland + musl + Buildroot 是最大不确定性"。没有放弃条件的 spike 会变成无底洞 —— 每周都能说"再调一下就好了"。

### 1.5 3.2–3.5 的依赖关系（保持原样）

```
3.1 spike ──► 3.2 Wayland 正式接入 ──┬──► 3.4 应用分发
                                     └──► 3.5 用户与会话
3.3 DRM/KMS + GPU（可与 3.1 并行做 damage 追踪部分）
```

**3.3 的"退一步"部分（全屏 damage 追踪 + 局部重绘）不依赖 Wayland** —— 它在当前 fbdev 路径上就能做，且直接改善 4K 下的滚动体验。**这是 Phase 3 里唯一可以现在就开工的部分**，建议单独立项，不要绑在 3.1 后面。

## 2. 4.4 自动化 VM 冒烟进 CI —— 评估

### 2.1 现状

`scripts/qemu-verify.sh` 已经能：开机 → 等桌面 → 截图 → 断言关键像素/日志。**"做什么"已经有了，缺的是"谁来定时做"。**

### 2.2 真正的障碍

| 障碍 | 说明 |
|---|---|
| **需要 KVM** | GitHub Actions 的免费 Linux runner **不暴露 `/dev/kvm`** → QEMU 只能 TCG 软件模拟，开机可能要几分钟，且帧率不代表真实硬件 |
| 构建机本身无 KVM | 项目现有的 VirtualBox 构建机也**没有** `/dev/kvm`（第四轮已记录） |
| 需要一个自托管 runner | 要么在少爷的机器上跑 runner（常开），要么用定时任务 |

### 2.3 建议

**方案 A（推荐）：本地定时任务，而不是 CI**
用 Windows 任务计划程序每天跑一次 `qemu-verify.sh`，结果写进 `docs/`。成本最低，且**能立刻开始**。

**方案 B：自托管 GitHub Actions runner**
少爷的机器常开时可行。但收益主要是"提交后自动出结论"，而当前开发节奏是单人 —— 定时任务已经够。

**不建议**：用免费 CI runner + TCG 模拟。跑得慢且结论不可信（帧率与真实硬件差一个数量级）。

## 3. 4.5 备份 / 快照 —— 评估

### 3.1 关键约束：ext4 没有快照

09-27 版写的是"ext4 快照或 tar 备份"。**ext4 本身不支持快照** —— 快照需要 LVM 或 btrfs。

| 方案 | 可行性 | 说明 |
|---|---|---|
| LVM 快照 | 需要安装器建 LVM 卷组 | **改动大**：`aether-install` 的分区逻辑要重写 |
| btrfs 快照 | 需要 btrfs 根分区 | 同上，且 btrfs 在嵌入式场景下不主流 |
| **tar 备份到第二分区** | ✅ 可行 | 不需要改分区布局，代价是"备份期间文件可能不一致" |

### 3.2 建议：先做 tar 备份，并把"一致性"这件事说清楚

**最小可用**：`aether-backup` 把 `/home` + `/etc/aether` tar 到第二分区（或外置盘），带校验和。

**必须诚实标注的边界**：tar 不是原子快照 —— 备份期间正在写的文件可能落在不一致的状态。对"用户文档"这个场景可接受（写文档时不会同时备份），对"数据库"不可接受（AetherOS 当前没有数据库）。

**验证要求**：4.5 的验收是"破坏性测试后能从备份还原到可用状态" —— 这**必须在实机上做**（要在真分区上删东西再还原）。
