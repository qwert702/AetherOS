# ADR：应用包签名与依赖解析强制接入安装前置

- 状态：**接受**
- 日期：2026-11-21
- 相关：`aetherd/src/apps.rs`、`scripts/mkapp.py`、`scripts/app-keygen.py`、`docs/应用包格式（APP-PACKAGES）-2026-09-28.md`、更新包验签（`aetherd/src/update.rs`）

## 背景

AetherOS 镜像里没有包管理器，"装应用"= 把一个目录复制到 `/var/apps/<id>/`。此前
`aetherd app install` 的防线只有：id 路径段校验、entry 路径穿越校验、拒绝包内符号链接、
ELF/脚本预检（缺库只给告警、仍可装上）。存在两个缺口：

1. **应用包没有签名**。从宿主/U盘/HTTP 拉进来的目录可以任意构造清单与可执行文件，
   安装端不验证"这份包是谁签的"。更新包链路在 2026-10-24 已接 Ed25519 验签，
   应用包链路一直没接。
2. **依赖解析算了不用**。`walk_dependencies` 能递归闭包找出既不在包内 `lib/`、
   也不在系统库目录的 soname，但预检只把它写进一句告警，安装照样继续 ——
   包装上去必然 `error while loading shared libraries`，却留给用户运行时才撞。

## 决策

1. **应用包强制 Ed25519 验签**，算法与更新包链路复用同一套 `ring` 范式
   （`ED25519` + `UnparsedPublicKey`，32 字节原始公钥内嵌，64 字节 detached 签名），
   不引入新的第三方 crate。
   - 签名文件：包根 `app.json.sig`；签名对象 = `app.json` 落盘后的**原始字节**
     （不做 JSON 规范化、不重排键序、不去末尾换行），签字两端逐字节对应。
   - 生产公钥：`aetherd/keys/app_pubkey.bin`（`include_bytes!` 内嵌）。当前入库的是
     **测试密钥，非生产**；生产私钥由 owner 离线保管，不进仓库/镜像/脚本目录。
   - 验签顺序固定：**先验签 → 再解析清单 → 再核对负载文件哈希**。签名不过就不许读
     清单字段，更不许往应用目录写任何东西。
2. **清单登记负载文件哈希**。签名包的 `app.json` 必须含 `files` 数组，逐项给出
   `path` / `sha256`（64 位小写十六进制）/ `bytes`。安装端逐项核对存在性、
   符号链接、大小、哈希；包内还不允许出现清单未登记的额外文件（防止清单之外夹带）。
3. **缺系统 soname 在安装阶段硬拒绝**。预检结论携带 `missing_libs` 列表；
   `install` 在复制之前发现非空即整包拒绝，错误信息列出全部缺失 soname，
   且不留下半个安装目录。glibc 家族夹带、terminfo 缺失仍维持 Risky 告警
   （这两类不阻断安装，分别有独立的处置提示）。
4. **打包器配套**：`scripts/mkapp.py` 增加 `--sign` / `--private-key`，写完包后
   登记 `files` 并对 `app.json` 原始字节签字产出 `app.json.sig`；新增
   `scripts/app-keygen.py` 生成 Ed25519 密钥对，私钥只写仓库外，公钥写 `.bin`。
   不加 `--sign` 仍可产出未签名包（向后兼容开发/自检），但目标生产策略会拒绝安装。

## 理由

1. **先验签后解析**：清单里的 id/entry/files 都是外部可控 JSON。若先解析再验签，
   攻击者可以用任意 JSON 触发解析器；这条顺序与更新包 `stage()` 的既有结论一致。
2. **复用 `ring`、不新增依赖**：`ring` 本来就在依赖树里（ureq→rustls→ring），
   自己实现密码学属于禁忌区；公钥内嵌与更新包同一套部署形态，运维认知一致。
3. **签名覆盖清单字节、哈希覆盖负载文件**：清单被改会直接验签失败；负载文件被换
   则由清单里的 sha256 兜住。两层各管一段，不把"整包哈希"塞进会被打包器改写的清单。
4. **缺库硬拒绝而不是告警**：实测这类包 100% 跑不起来，"先装上再说"把失败推迟到
   用户运行时，只会让人觉得系统坏了；安装前拒绝、并给出静态链接或补 `.so` 两条出路，
   可操作性更强。
5. **私钥不入库**：仓库可读、可随镜像分发；私钥一旦进仓库等于签名能力扩散。
   测试密钥与生产密钥分渠道，文档明确标注，避免误用测试私钥签发布包。

## 后果

- `aetherd app install` / AI 工具 `app_install` 只接受签名包；未签名、签名不符、
  公钥不符、清单被改、文件哈希/大小不符、夹带未登记文件、缺依赖 soname 全部整包拒绝，
  错误信息为中文并指明原因。
- 打包流程增加一步签名：发布机持有离线私钥，`mkapp.py --sign --private-key ...`；
  公钥轮换需要走发布流程，旧客户端在轮换后不再接受新包。
- 既有未签名样例包在目标端无法直接安装，需用 `--sign` 重打；开发机单测使用内存内
  生成的测试密钥对，不依赖仓库内私钥。
- 不改变既有符号链接拒绝、entry 路径穿越校验、glibc 家族告警、terminfo 预检等行为；
  不改动更新包验签逻辑。

## 验收

- `cargo test -p aetherd --locked` 全绿，且新增覆盖：未签名、签名错、清单篡改、
  公钥不符、哈希不符、依赖缺失被拒、正常签名包通过；
- `cargo clippy -p aetherd --all-targets --locked` 0 error；
- `python scripts/app-keygen.py --help`、`python scripts/mkapp.py --help` 可运行；
- 本决策与签名字节范围、命令、失败模式表一并写入
  `docs/应用包格式（APP-PACKAGES）-2026-09-28.md` 的「签名与验签」章节；
- 未新增第三方 crate，未改动 `Cargo.toml` / `Cargo.lock` 版本号。
