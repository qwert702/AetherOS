## 三、首次部署暴露的 3 个真缺陷（都在 `scripts/deploy-site.py`）

**① 校验与 dump 用错了二进制。** 这台机器上 PATH 里的 `nginx` 是 **1.24.0（没编 `stream` 模块）**，
而**正在跑**的是 `/www/server/nginx/sbin/nginx -c /www/server/nginx/conf/nginx.conf`（宝塔构建，有 `stream`）。
拿 PATH 里那个去测宝塔配置 → `unknown directive "stream"` —— **一个根本不存在的故障**。
→ 改成从 master 进程命令行里取 **(二进制, 配置)**，校验与 dump 都用它们。

**② vhost 写进了不会被加载的目录。** 宝塔的 nginx.conf 只 `include /www/server/panel/vhost/nginx/*.conf`，
**不读 `/etc/nginx/conf.d/`**；而 `nginx -t`/`-T` 默认测的又是 `/etc/nginx/nginx.conf`（它 include conf.d）。
两者不是同一个文件 → 老逻辑形成**两层假绿**：`nginx -t` 说 OK、站点照开、脚本打印"部署成功"，
而写进去的配置**永远不会生效**。
→ 改成**问运行中的 nginx**：`<它的二进制> -T -c <它的配置>`，从输出里的
`# configuration file <路径>:` 注释头认出**真正生效的那个 vhost 文件**。

**③ reload 只有两种方式，这机器两种都不成立。** nginx 不在 systemd 下（`systemctl is-active` = inactive），
`/run/nginx.pid` 是 **0 字节**（2026-10-03 留下的）→ `systemctl reload` 与 `nginx -s reload` 双双失败
（`invalid PID number "" in "/run/nginx.pid"`）。
→ 加第三条路：**直接给 master 发 HUP**，并用 worker 换代作为"真的生效"的判据；
三种都不成立时**显式拒绝**（生产机上盲重启会与既有实例抢端口）。

**另外加了一条保护**：生效的 vhost 若**已带 TLS 段（certbot 管理）**，脚本**绝不覆盖**它
（那里面有 certbot 插的 `listen 443` 与证书路径，覆盖=把 HTTPS 弄没），
改为**校验**它与本站一致（root、安全头片段），不一致就报错让人工处理 —— 脚本不猜。

判据：`scripts/deploy-site.py --selftest`（9 项：生效 vhost 识别 + 运行中进程识别，**不需要服务器与凭据**）
已进 `gates.py`（**34 → 35 项**）。
