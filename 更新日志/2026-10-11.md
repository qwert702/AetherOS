## 十二、同日晚些时候：在 VMware 里看到"今天的构建"（ISO 重建实战）

**起因**：你要求在 VMware 里看效果。已发布的 ISO 是 **2026-10-02** 的，今天改的双语通知
根本不在里面 —— 软件镜像不会跟着源码自己变，所以只能**真的重建一次**。

**结论先说**：重建成功，**新构建已在 VMware 里启动**：`42,991,616` 字节 ·
`sha256=162b19a79…` · offset 510 = **`55aa`**（isohybrid 生效，可 dd 到 U 盘）。
代价是一路上撞出 **4 个真缺陷**，其中两个让 ISO **根本构建不出来**、
一个把**装机前提**静默堵死。

### 12.1 环境层（不是项目代码问题，是这台机器的现状）

| 卡点 | 根因（实测确认） | 我的处置 / 你怎么撤销 |
|---|---|---|
| 构建机起不来 | 保存状态 `uApicMode: saved=3 config=2`（旧版 VirtualBox 写的），**无法恢复** | `discardstate` 后重开机；磁盘上的 Buildroot 树（12 GB）不受影响 |
| SSH 永远连不上 2222 | **Windows 保留了 TCP 2180–2279**，2222 正落在里面 → `VERR_NAT_REDIR_SETUP` | 新增转发 **22022**（原 2222 规则保留未动，可随时回退） |
| 主机密钥拒连 | 严格校验按 `host:port` 记账，换端口即新条目 | 把 2222 那条密钥**按端口复制**一份；**没有**删记录走 TOFU（那等于静默信任新密钥） |
| 密码忘了、`秘钥.md` 是 0 字节、VM 里只有 SHA-512 哈希 | 无人值守安装不留明文口令（设计如此） | **本地控制台恢复**：GRUB → `e` → `linux` 行尾加 `rw init=/bin/bash` → `Ctrl+X` → root shell → **注入你自己的公钥**（`/home/aether/.ssh/authorized_keys`，80 字节、600、aether:aether）。**没有改口令**；撤销 = 删掉那一行 |
| `vm.py` 跑不了 | dsh 内置 Python 没装 paramiko | 改用系统里 `D:\py\python.exe`（paramiko 5.0.0） |
| headless 也能恢复 | —— | `VBoxManage controlvm <vm> screenshotpng` 看画面 + `keyboardputscancode` 注入按键；**按下/松开必须分两次调用**（同一批里发 press+release 会被"按状态轮询"的实现漏掉，实测踩到过） |

### 12.2 代码层：两个让 ISO **构建不出来**的缺陷（台账 #53）

`[1/3]` 阶段就失败，报 `cannot find module or crate libc`：

1. `aetherd/src/timesync.rs` 在 `#[cfg(unix)]` 里调 `libc::clock_gettime/clock_settime/adjtime`，
   而 **`aetherd/Cargo.toml` 里没有 `libc`**；
2. 补上依赖后暴露第二个：同一个 `#[cfg(unix)]` 函数的 `match how` **没覆盖 `Adjustment::Refused`（E0004）**；
3. 外加 musl 下 `libc::time_t` 已废弃（项目要求 0 告警）→ 改写成 `as _`，让字段类型说话。

**为什么能藏 8 天**（这是本条最值得记的部分）：
那段代码在 `#[cfg(unix)]` 里 → **Windows 构建根本不编译它**；
`musl-warn-check.py` 又**特意跳过 `aetherd`**（ring 需要 musl-gcc）；
单测也全在 Windows 上跑。**三条判据同时漏掉**，于是从
**2026-10-03（加 SNTP 对时那天）到 10-11，ISO 一直是构建不出来的** ——
台账 #33「ISO 未重构建」的真正代价就在这里。

> **教训**：`#[cfg(unix)]` / `#[cfg(target_os = "…")]` 这类平台分支，
> **必须在那个平台上真正编译一次**才算存在。本次新增的 `crate-dep-check.py`
> 只能挡住"用了没声明"这一半；另一半（非穷尽匹配之类）**只能靠真的跑一次 `[1/3]`**。

### 12.3 工具层：两个让构建**看起来成功**的缺陷（台账 #54）

| 现象 | 根因 | 证据 |
|---|---|---|
| 构建跑到 `target-finalize` 报 `post-build.sh: Permission denied`（Error 126） | SFTP 不保留可执行位，而 `vm-sync.py` 的白名单**只有** `platform/overlay/init` | 修复后同步输出 `已按 git 索引 恢复 45 个文件的可执行位` |
| **构建报 PASS，日志里却没有 `isohybrid` 那一行**，产出的 ISO 前 512 字节全零 | 跳过规则写成**字符串前缀**：`startswith(("platform/build", …))` 把 **`platform/build-iso.sh`** 也跳掉了 → 构建机一直用 **2026-09-30 的旧脚本**（**没有** isohybrid + MBR 自检，那是 10-02 审计 H-6 才加的） | 修复后同步数 **564 → 565**（多的正是它）；日志第 394 行出现 `==> isohybrid 完成，MBR 签名自检通过`；ISO `42,137,600 → 42,991,616` 字节；offset 510 = `55aa`；446 处有隐藏 ISO 分区表 |

**这解释了 README 里那句"当前 ISO 不能 dd 到 U 盘"的真正原因** ——
不是"还没做 isohybrid"，而是**那段代码从没被同步到构建机上**。
`aether-install` 的装机前提（M6 源镜像带 MBR 签名）因此被静默堵死，
而**没有任何判据会响**：构建报 PASS、门禁全绿、台账还把"MBR 自检"写进验收。

修复：跳过改**路径段**比较；可执行位改由 **git 索引的 100755 位**驱动
